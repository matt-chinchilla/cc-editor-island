- **Keep groups and Apply block layouts** (island `v0.2.3-cc25`, unit i-block-layout, on an engine with the marker `kicadBoardUpdateGroups`, engine run 15; a host gates both on `ev.ready` `caps` listing `blockLayouts`): both ops also take KiCad's two boxes of Update PCB from Schematic, `transferGroups` (Keep groups: the schematic's groups become groups of the board, each keeping its design block link) and `applyBlockLayouts` (Apply block layouts: each such group takes its block's layout), booleans, `applyBlockLayouts` only beside `transferGroups` (alone, or `true` beside `transferGroups` false, answers `bad_args`). With `transferGroups` true the answer adds `layouts: { applied: number, failures: [{ uuid: string, reason: string }] }`: a preview always `{ applied: 0, failures: [] }`, an update how many groups took their layout and each that did not (the group's uuid on the board, KiCad's reason, at most 1,024 characters, at most 4,096 failures listed). An update with layouts is KiCad's Update step plus one step per laid out group. An update whose two boxes differ from its preview's answers `stale`. With `transferGroups` false, or neither box sent, the run and its answer are today's, on any engine. A group's block row must be loaded (`project.libs`) for its layout to apply. On an engine without the marker (engine run 14) a request with `transferGroups` true answers `unsupported` "kicadBoardUpdateGroups" after its args are checked.

### block.applyLayout

Island `v0.2.3-cc25`, in a `pcb` frame, on an engine with `kicadDesignBlockApplyLayout` and `kicadCollabBusy` (engine run 15, unit e-block-layout); a host gates it on `ev.ready` `caps` listing `blockLayouts`, which a `pcb` frame lists when its engine also takes Keep groups and Apply block layouts on `board.preview` and `board.update` (above). It runs KiCad's Apply Design Block Layout over the groups asked with no KiCad window: each group linked to a design block is laid out again as its block's layout, as ONE undo step.

- `uuids`: 1 to 256 groups of the board, lower case, none twice. Each group's design block row must be loaded in the engine (`project.libs` naming the block's library), as a group placed with its block's nickname is.
- The answer is `{ applied, failures }`: how many groups took their layout, and each group that did not, with KiCad's reason (at most 1,024 characters). It comes once the engine's apply queue is empty and the run's record is there. A group placed from a block whose layout lacks a part the schematic names (a group made by `board.update` with Keep groups) fails with KiCad's reason; one placed from that same block's own layout applies.
- The checks, in order, every one before any effect: the args (`bad_args`, `message` the op); the frame (`unsupported`, "a design block layout is applied in a pcb frame"); the engine (`not_ready` before it is up; `unsupported` naming the first missing export, so on engine run 14 `unsupported` "kicadDesignBlockApplyLayout"); a document open (`not_ready`); a load parked, a popup menu, a dialog up or a placed item on the pointer (`busy`). Then `block_failed` when the engine refuses a uuid naming no group ("a uuid names no group of the board"), when nothing applied and no failure is named (KiCad's line, "No groups with a linked design block are selected." for groups with no link), or when a window of KiCad's showed during the run (closed without accepting it, `message` its title); `not_applied` when no record comes within about 30 s; `island_error` for a record of another shape.
- The run's folder under `/tmp/cc-blocklayout/` is removed after every answer.
