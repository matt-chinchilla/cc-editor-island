### libs.remove and paths.set
The run time rows of KiCad's library tables, the host's side of Setup's Sources and Paths, in a `sch` or a `pcb` frame (island `v0.2.3-cc25`, on an engine with `kicadLibsRemoveEntry`, `kicadLibsAddEntry` and `kicadCollabBusy` for `libs.remove`, `kicadPathVarsSet` and `kicadCollabBusy` for `paths.set`, engine run 15; a host gates them on `ev.ready` `caps` listing `libRows` and `pathVars`, listed by `sch` and `pcb` frames only). Any other frame answers `unsupported`. Neither needs a document open. The checks, in order, every one before any effect: the args (`bad_args`, `message` the op); the engine (`not_ready` before `ev.ready`; `unsupported` naming the first missing export, so on engine run 14 `libs.remove` answers `unsupported` "kicadLibsRemoveEntry" and `paths.set` `unsupported` "kicadPathVarsSet"); a load parked, a popup menu or a dialog up (`busy`).

- `libs.remove { kind, nickname }` takes back a row `project.libs` added at run time: `kind` `symbol`, `footprint` or `block` (a design block library), `nickname` as `project.libs` takes one. The engine erases the row from its live table and drops what it loaded from it; KiCad's choosers no longer list it. The answer `{}` comes once the engine's apply queue is empty. `not_found` (`message` the nickname) when the engine holds no run time row of that kind and name: a row the boot made (KiCad's own set, the project's tables as KiCad loaded them) is never removed. A later `project.libs` naming the nickname adds its row again. Past about 10 s with the queue still busy: `island_error`.
- `paths.set { vars }` sets path variables as KiCad's Configure Paths sets them: `vars` maps 1 to 64 names to folders of the project. A name is KiCad's form (`^[A-Z][A-Z0-9_]{0,63}$`) and never one of KiCad's own (`KIPRJMOD`, `KICAD_USER_TEMPLATE_DIR`, `KICAD_PTEMPLATES`, and for KiCad 6 to 10 the versioned `SYMBOL_DIR`, `FOOTPRINT_DIR`, `3DMODEL_DIR`, `TEMPLATE_DIR`, `3RD_PARTY` and `DESIGN_BLOCK_DIR`); a folder is a path in `project.open`'s normal form, relative to the project folder (not `${KIPRJMOD}`: a design whose project file sits in a subfolder names the subfolder). The frame hands the engine each folder made absolute in its file system; every library row naming one of the variables (`${NAME}`) loads again, so a row that found nothing before now loads. A variable is never removed; a later `paths.set` of the same name replaces its folder. From the answer on, the frame's `project.libs` resolves rows `${NAME}/...` of the project's tables into that folder too. The answer is `{ set }`, the names in the order sent, once the engine's apply queue is empty; `not_applied` when the engine refuses the call or its queue stays busy past about 10 s (nothing set on the island's side when refused).
<!-- part: notes project.libs -->
- Widened (island `v0.2.3-cc25`, unit i-librows). The answer is `{ symbol, footprint, block }`: `block` lists the nicknames registered as design block libraries, `[]` when none.
- `vars` (optional): 1 to 64 path variables, each name and folder as `paths.set` takes them. Before the nicknames are read, the frame resolves rows `${NAME}/...` of the project's tables into the folder named, so a library the design keeps under a variable of its own is served as a project library is (its row type `KiCad`, the path in the normal form ending as the kind asks). The variables stay set for the frame's later `project.libs`; a request refused puts back the ones it set. They are the island's alone: only `paths.set` hands them to KiCad.
- A nickname may name a row of the project's `design-block-lib-table` in `${KIPRJMOD}` (or under a variable): type `KiCad`, a path ending `.kicad_blocks` that names a folder there. The engine adds a row of that nickname to its design block table whose uri is that folder (the widened `kicadLibsAddEntry` with the kind `design_block`), and KiCad's own reader reads the blocks from it. A nickname naming a block row again is taken out first (`kicadLibsRemoveEntry`) and added again, so KiCad reads the folder anew. On an engine without `kicadLibsRemoveEntry` (engine run 14) a request naming a block row answers `unsupported` "kicadLibsRemoveEntry" and nothing is added.
- A request with no `vars` naming no block row is answered exactly as before, with `block: []`. Otherwise the checks, in order, before any effect: the args; the engine (`not_ready`, `unsupported`); each nickname (`not_found` for the first that names no library with the variables applied); busy; then the symbol and footprint libraries take the checks and effects above, and the block rows are added. The answer waits for the engine's apply queue to empty.
