<!-- part: notes sim.run -->
- **The run guard** (island `v0.2.3-cc25`). Every `ev.sim` is keyed by its run number: a `loading` or `running` event goes out only for the run live at that moment, and an end only while no other run is live, once per run, never for a run older than one whose end went out (the numbers only grow). Anything else is dropped, so nothing of run N can move or end run N + 1, whatever reaches the island late. Two runs started back to back each end once with their own number (`tests/e2e/lo/sim-faults.spec.ts`).
- **The problems of a fault** reach the host through the codes above: with engine run 15 a part with no simulation model is a `no_model` problem naming it (Glasgow: U1 among them), and a model file the project does not hold (`Sim.Library`) is a `file_missing` problem naming the part and the path, with no KiCad box: the next op is answered at once.
- **Pole-zero and S-parameters, measured with a real result** (engine run 14, 2026-11-18): pole-zero on `sim-rc` (V1 given an AC magnitude of 1) answers one plot with one complex vector `pole(1)`, minus 1,000 + 0j per second, minus 1/RC; without an AC magnitude on the input source ngspice answers "The input signal is shorted on the way to the output" and the run ends `failed`. S-parameters on the island's `sim-sparam` fixture (a 100 nH and 40 pF low-pass between two port sources, `portnum` and `z0` 50 in `Sim.Params`) answer the `S_i_j`, `Y_i_j` and `Z_i_j` vectors of both ports, complex, against `frequency`: `|S21|` 1.0000 at 1 MHz and 0.0127 at 1 GHz.
<!-- part: notes sim.stop -->
- **A Stop the service cannot carry out** (island `v0.2.3-cc25`, docs/si1-stop-diagnosis.md). A Stop reaches ngspice as a request to the service's worker, and the engine then waits for ngspice's thread to end. Measured on engine run 14 with 1 ns steps over 200 ms or 2 s, the run then never ended: ngspice's output storage grew to the service's 4 GiB memory within about 2 s (at 4 to 6 percent), and either the worker answered nothing more, the halt included, or ngspice's allocation failed ("malloc: can't allocate"), its thread ended "awaiting to be reset" and no record came. So after a Stop, while the run is still live, the island reads the worker every 300 ms: while ngspice runs it is left to end the run; a worker that does not answer within 250 ms, or whose ngspice runs nothing while the engine is idle twice in a row, is ended (as `sim.release` ends it, which settles what the engine waits on) and the engine is asked to stop again: it finds no run in the fresh service and finishes the run. Measured with 1 ns over 2 s stopped at 6 percent: the end 555 ms after the press, and the next run `done` 204 ms after its request on a fresh worker (`tests/e2e/lo/sim-faults.spec.ts`). The end's phase is the engine's record: on engine run 14 it read `done` (the finish was queued when ngspice's thread ended on its allocation failure); engine run 15 ends such a run `stopped` or `failed`. The ended worker's vectors go with it, and the next run boots a fresh worker.
