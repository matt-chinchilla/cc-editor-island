### sheet.pins.get
Each sheet's pins against the hierarchical labels of its own file, read in a `sch` frame with a schematic open (island `v0.2.3-cc25`, on an engine with `kicadSheetPinsGet`, engine run 15; a host gates it on `ev.ready` `caps` listing `syncPins`, listed by `sch` frames only on an engine with `kicadSheetPinsGet`, `kicadSheetPinsApply`, `kicadSheetPinsPlace`, `kicadCollabBusy` and `kicadCollabGetSelection`). No args (every sheet of the design), or exactly `{ sheets }`: 1 to 4,096 of exactly `{ uuid, sheetPath }`, the sheet's uuid (lowercase) and the path the sheet sits on, as a read answers them; a sheet asked that the design does not hold is left out. The checks, in order: the args (`bad_args`); the frame (`unsupported` "a sheet pins op runs in a sch frame"); the engine (`not_ready`, `unsupported` naming `kicadSheetPinsGet`); a schematic open (`not_ready`); a load parked, a popup or a dialog up, or an item hanging off the pointer (`busy`). A read: answered during a `sheet.check`.

One row per sheet instance: `sheet` its uuid, `sheetPath` the path it sits on (`/` for the root, then `/<uuid>/` per level), `name` its sheet name, `file` its file, and `pairs` (at most 4,096; `truncated` true when a sheet had more), paired by name as KiCad's Sync Sheet Pins window pairs them: a pin and a label of the same name and shape first, then a pin and a label of the same name whose shapes differ (one row, the two shapes apart), then each pin or label alone, its other side `null`. `pin` and `label` are uuids (lowercase); `PortShape` is one of `input`, `output`, `bidirectional`, `tri_state`, `passive`, present exactly where its side is. Two names that differ are two rows: a host that pairs them sends the rename. An engine answer of another shape is `island_error`.

### sheet.pins.apply
The host's changes to sheet pins and hierarchical labels as ONE commit "Synchronize sheet pins" (one undo step, where KiCad's own window commits each change apart), in a `sch` frame with a schematic open (island `v0.2.3-cc25`, on an engine with `kicadSheetPinsApply` and `kicadCollabBusy`, engine run 15; cap `syncPins`). The args are exactly `{ actions }`, 1 to 4,096 of:

```ts
type SyncAction =
  | { op: 'renamePin'; pin: string; to: string } | { op: 'renameLabel'; label: string; sheetPath: string; to: string }
  | { op: 'shapePin'; pin: string; to: PortShape } | { op: 'shapeLabel'; label: string; sheetPath: string; to: PortShape }
  | { op: 'removePin'; pin: string } | { op: 'removeLabel'; label: string; sheetPath: string };
```

each with exactly its keys: uuids lowercase as `sheet.pins.get` answered them, a label's `sheetPath` the path of the sheet that HOLDS it (the row's `sheetPath` followed by the row's `sheet` and a slash), a name 1 to 1,024 characters with no control character. The checks, in order: the args (`bad_args`); the frame; the engine (`not_ready`, `unsupported` naming the first missing export); a schematic open (`not_ready`); `busy` as for `sheet.pins.get`, and during a check or an import.

The frame queues the run with a fresh `/tmp/cc-sheet-pins/<n>/` for its record, waits for the apply queue to empty and the record, and removes the folder whatever the answer. Every pin and label named must be in the design (a label on its sheet path): else the engine refuses the whole run and the answer is `not_applied` with nothing changed. A pin is removed as KiCad's own delete removes one. The answer counts the actions applied (an action on an item an earlier action of the same request removed is skipped); an `ev.edited` follows once the depth moved. `not_applied` also when no record came within about 30 s; `island_error` for a record of another shape.

### sheet.pins.place
The missing side placed by KiCad's own placement tools, in a `sch` frame with a schematic open (island `v0.2.3-cc25`, on an engine with `kicadSheetPinsPlace`, `kicadCollabBusy` and `kicadCollabGetSelection`, engine run 15; cap `syncPins`). The args are exactly `{ sheet, sheetPath, place, names }`: the sheet's uuid and the path it sits on as a read answered them, `place` `pin` (a sheet pin on the sheet for each name, named and shaped after the sub sheet's hierarchical label of that name) or `label` (a hierarchical label inside the sheet for each name, after the sheet's pin of that name), and 1 to 64 names. The checks, in order: the args (`bad_args`); the frame; an item of ours still hanging off the pointer is dropped first (`busy` when it would not go); the engine (`not_ready`, `unsupported` naming the first missing export); a schematic open (`not_ready`); `busy` as for `sheet.pins.get`. `not_applied` when the sheet is not there or a name has no counterpart (nothing armed), or when the editor did not run the tool.

KiCad's window never opens. For `label` the editor enters the sheet and the first label hangs off the pointer: the answer `{ hanging: true }` comes once it does, the placement joined to the place watch (`busy` everywhere while it hangs, Esc drops it and leaves the tool, a press commits one undo step and the next name hangs, the tool ending after the last); `busy` when it never hangs within about 10 s. For `pin` the editor shows the sheet's own level with the sheet chosen, and KiCad's sheet pin tool makes its item at the reader's first press on the drawing, at the sheet's edge: the answer `{ hanging: false }` comes once the tool runs with nothing hanging yet, `{ hanging: true }` (joined to the watch) when an item already hangs. Each press after that places the next name; Esc ends the placement and nothing stays armed.

- **Held**: while `ev.ready` lists `syncPins` in a `sch` frame, KiCad's Sync Sheet Pins (`eeschema.InteractiveDrawing.syncSheetPins`) and Sync All Sheet Pins (`eeschema.InteractiveDrawing.syncAllSheetsPins`, seeded Ctrl+Alt+Y) are held: KiCad's window never opens, the frame sends `ev.held { action }` and the host opens its Sheet pins page over the three ops. On an older engine (run 14 and before) the cap is absent, the two actions are KiCad's own, and the three ops answer `unsupported` naming the first missing export.
