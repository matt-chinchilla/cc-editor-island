### KiCad never shows: held menus and toolbars (`heldMenus`)

Island `v0.2.3-cc25`. Our engine from run 15 (kicad `cc/main` K-HOLD, in `ACTION_MENU::OnMenuEvent` and `ACTION_TOOLBAR`'s press handling) asks the frame for every menu item and toolbar button a press resolves to, through the same slot keys use since run 12 (`ev.held` above): a held action is taken from a key, a menu bar item, a toolbar button and an item of KiCad's own context menus alike, the press is dropped, and the frame sends one `ev.held { action }`. KiCad's context menus still open (they are reported as `ev.menu` as before); only a held item inside one is taken. The 45 items of KiCad's Preferences > Set Language are a wx menu range, not tool actions: the engine asks for any of them as one name of ours, `cc.Control.setLanguage`. The engine says it asks with the marker export `kicadHeldMenus`; `ev.ready` lists the pseudo-cap `heldMenus` in a `sch`, `pcb` or `symedit` frame exactly when the engine has `kicadHeldMenus` and `kicadHostActions`. A host shows KiCad's menus (`chrome.show`) with a held action's door gated on this word: where it is absent (engine run 14 and older) a menu or toolbar press still reaches KiCad's window, and only keys are held.

Held with nothing of the host's to open (the host answers each `ev.held` with nothing, or a short line of its own): `cc.Control.setLanguage` (every editor frame, under `heldMenus`: the menus stay in English), `eeschema.RemoteSymbols.showPanel` (`sch`, the Remote Symbols panel), `common.API.pluginsReload` (`sch` and `pcb`, Refresh Plugins), `pcbnew.ScriptingTool.pluginsShowFolder` (`pcb`, Open Plugin Directory) and `pcbnew.Control.showPythonConsole` (`pcb`, the scripting console), the last four under `heldKeys`. The island runs no Python and no plugin API, so these windows would show nothing that works. Every other action a wave 2 door replaces is held by that door's own rows; the island reads every row as one table, so a host that lists its doors reads the same union.
