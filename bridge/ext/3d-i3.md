- `ev.export { job: string, phase: "loading" | "models" | "running", percent?: number }`: the progress of a `project.export` run of `pcb_export_3d` or `pcb_render`, at most every 250 ms, exactly these keys. `loading` while the 3D service's files load (percent of bytes), `models` while the bodies the board's model lines name are staged (percent of files), `running` from the render's `Rendering <n> percent` lines read from the run's folder while it goes; an engine that writes them only into the run's final record (every engine run 15 build through T3) gives no `running` phase. The same phase and percent is never sent twice in a row.
<!-- part: notes project.export -->
- The 3D outputs (island `v0.2.3-cc25`, engine run 15): the job `pcb_render` (KiCad's raytraced picture of the board, `format` `png` or `jpeg`; `jpg` is refused), listed in `island.json` `exportKinds`; a host gates it on `ev.ready` `caps` listing `render` (the engine's `kicadOutputJobs()` lists `pcb_render`). The picture has KiCad's own size, not the asked one: KiCad's raytracer draws in whole blocks, so an asked 1600 by 1200 gives 1568 by 1176 and 800 by 600 gives 784 by 592, as `kicad-cli` 10.0 writes. The engine names the size in its line "The picture is <w> by <h> pixels.", an info line the answer does not carry; it equals the file's own header (a PNG's IHDR, a JPEG's frame header), which is where a host reads it.
- Before a `pcb_export_3d` or `pcb_render` run the island stages the bodies the board's shown model lines name, read from the LIVE board (the engine's `kicadBoardModels`: a part or a body given since the last save included, nothing saved, the board's modified state unchanged; the saved board's lines only on an engine that cannot read them then), a model file the page added with `project.write` found in the project folder before any save: a `${KICAD*_3DMODEL_DIR}` line through the model store (its body written under `/pcbjam/3dmodels/<Lib>.3dshapes/`), a `${KIPRJMOD}`, `$(KIPRJMOD)` or bare relative line copied from the project folder to `/pcbjam/3dmodels/kiprjmod/<relative path>`; a `kicad-embed://` line needs nothing; an absolute path, another variable or a path leaving the project resolves to nothing. The formats the 3D service makes are handed the same bodies, each by its path relative to `/pcbjam/3dmodels` (`kiprjmod/<relative path>`, `<Lib>.3dshapes/<Name>.<ext>`), the only paths the service stages. At most 2,000 files and 512 MiB; the lines past them, and the bodies not found, go into the file without a body. KiCad's own warning for such a body ("Could not add 3D model for R1. File not found: ...") reaches `notes` from a `pcb_render` (a body the render cannot load is a warning line); from a format the 3D service makes it is not carried on engine run 15 (the service answers its report as one text, which the engine reports as an info line, and `notes` holds the warning and error lines only).
- Without the cap `occ`, every `pcb_export_3d` runs with `cc_occ: false` in its settings (engine run 15 takes it and never names it in `dropped`): only VRML is made then (a full `.wrl` on engine run 15: about 18 MB on Glasgow, as `kicad-cli` 10.0.4 writes), every other format answers `export_failed` with the line "Only VRML is made here."
- Each job's time bound comes from `bridge/exportTiming.json` (`island.json` `timing.exportMs`): `pcb_export_3d` and `pcb_render` five times their slowest measured run, at least 60 s and at most 900 s; every other job 45 s.
- Held in a `pcb` frame, each sending `ev.held` and opening nothing: KiCad's File > Export > STEP (`pcbnew.EditorControl.exportSTEP`) and VRML (`pcbnew.EditorControl.exportVRML`) under the cap `export` (the host's Outputs page opens on 3D model for CAD and on VRML), and KiCad's 3D viewer's Export Image (`3DViewer.Control.exportImage`) and Copy 3D image (`3DViewer.Control.copyToClipboard`) under `heldKeys`, with no door of the host's.
