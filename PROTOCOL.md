The message protocol between a page (the host) and the editor island (the frame). The island is a cross-origin iframe. All messages are structured-clone objects. File contents travel as `Uint8Array`, in both directions; the host may transfer the underlying buffer, and the frame always transfers a fresh copy. The one exception is `project.write`, whose files carry their text as a string (UTF-8 on the frame's side).

The frame's kind is fixed by its URL: `?frame=sch` (the schematic editor, files `.kicad_sch`) or `?frame=pcb` (the board editor, files `.kicad_pcb`); anything else means `sch`. `?theme=night` starts it dark, anything else light.

## Handshake
1. The frame posts `{ type: "cc.hello", proto: 1, nonce: <random string>, island: <islandId> }` to `window.parent` with the host's exact origin as target. It does so before the engine boots.
2. The host answers `{ type: "cc.connect", nonce }` to the frame's window with one transferred `MessagePort`. The frame accepts only the first connect carrying its nonce, from `window.parent`, with no other keys. A reloaded frame posts a new hello with a new nonce.
3. Everything after runs on the port. Events the frame emitted before the connect are queued and sent, in order, once the port arrives.

## Requests (host to frame): `{ id: number, op: string, args?: object }`
Answers: `{ id, ok: true, result: object }` or `{ id, ok: false, error: { code: string, message: string } }`. Every request with a safe integer `id` and a string `op` is answered exactly once; anything else on the port is ignored. The frame handles requests one at a time, in the order they arrive: a request waits until the one before it has been answered. The library reads `lib.index`, `lib.item` and `lib.prefetch` are the exception: they never touch the engine, so each is answered as soon as its read is, outside that queue (a `lib.item` waiting on a bundle holds up no `key.press`, `view.fit` or `place` sent after it, and none waits for them), and their answers may overtake earlier requests' answers. `keys.claim` is answered at once as well, outside the queue (it changes only which keys the frame hands to the host, never the engine), during an import or a check too. The one exception is a running `project.import`: the requests that arrive while it runs are answered at once (`busy`, or a `shutdown`'s own answer), before the import's answer.

### project.open
- Every open starts from an empty project folder: the previous project's files are removed first.
- `files` holds at most 4096 entries and `name` at most 255 characters. Each `bytes` must be a `Uint8Array`; a bare `ArrayBuffer`, or any other value, answers `bad_args`.
- Paths are relative, POSIX, no `.` or `..` segments, no empty segment, no leading slash, no NUL, at most 255 bytes in UTF-8. A path the frame rejects, or one the file system refuses, is reported in `dropped` and never written.
- `open`, when given, names the file KiCad opens. It must end with the frame's own extension (`.kicad_sch` in a `sch` frame, `.kicad_pcb` in a `pcb` frame) or the request answers `bad_args`, so a later `project.save` can never write one kind of file into the other. It must be one of the written files, or the open answers `open_failed`.
- Without `open`, the frame opens the file of its own kind that shares the base name of a `.kicad_pro` in `files` (the project's root sheet or board), else the first file of its own kind, else answers `nothing_to_open`.
- `opened` is the normalized path KiCad opened.
- Before the load the frame writes KiCad's local display settings, `<stem>.kicad_prl` beside the file it opens (KiCad loads the project named after that file, settings included), with every display opacity at 1 (`board.opacity` zones, pads, tracks, vias, images and shapes), so the board draws as the site's viewer draws it: KiCad's own defaults draw zones and images at 0.6. Since island `v0.2.3-cc9` it also lists `board.visible_items`: every one of KiCad's visibility items but `drawing_sheet` (`tracks`, `vias`, `pads`, `zones`, `shapes`, `bitmaps`, `footprints_front`, `footprints_back`, `footprint_values`, `footprint_references`, `footprint_text`, `footprint_anchors`, `ly_points`, `ratsnest`, `drc_warnings`, `drc_errors`, `drc_exclusions`, `locked_item_shadows`, `conflict_shadows`, `board_outline_area`, `grid`: the engine's own names, its `VISIBILITY_LAYER` enum lowercased), so the board editor draws no page frame (no border, margins, title block or page edge), as the site's viewer draws none. KiCad shows exactly the items listed (without the key it shows all of them), so every other item draws as before. A schematic has no such setting; its frame is transparent in the island's palette instead (`README.md`, Theme). A `.kicad_prl` of that path in `files` is kept as sent. The file is the engine's display state, not the design: no answer names it, and a save of it is never an `ev.saved` or listed in `saved`.
- `chrome` says whether any of KiCad's own window chrome (its menu bar, toolbars, status bar or infobar) is visible when the open answers. While the chrome is meant hidden, the frame hides it once more after the load and answers at once with what is visible then: no answer waits for a watch (island `v0.2.3-cc22`; before it the frame watched the chrome for about 1.5 s first, so every open answered about 1.5 s after its load). `true` means the engine would not hide it: a host that wants the chrome hidden sends `chrome.show { on: false }` again. What KiCad shows after the answer is not in `chrome`. Our engine (from run 9, the one with `kicadChromeShown`) holds its hidden chrome itself: it hides again inside the call that showed it, before a frame is drawn, and any real flip is an `ev.chrome`. For an engine without that, the frame watches the chrome for about 1.5 s after the answer and hides it each time KiCad shows it again; that watch ends at `chrome.show { on: true }`, at `shutdown` and when the frame goes, and there is never more than one. After `chrome.show { on: true }`, `chrome` is simply whether it is visible. An older island answers without the field; a host treats it as unknown.
- A host never sends `project.open` over a live document: to show another project it reloads the frame (or removes it and makes a new one). If it does send one while the open document holds unsaved edits, KiCad raises its own "Save Changes?" dialog inside the frame; the open may answer before the dialog is closed, and `project.open` and `project.save` answer `busy` until the user closes it.

### project.import
Converts a design drawn in another EDA tool into a KiCad document through the engine's own importers, and makes it the frame's document: a board in a `pcb` frame, a schematic or an Altium project's schematics in a `sch` frame. The `sch` frame, `sheets`, `project` and the Altium and SolidWorks board kinds were added in island `v0.2.3-cc8`; an older island answers a `sch` frame's import `unsupported`. A host can tell the schematic import from `ev.ready` `caps` (`kicadImportSchematic`).

- `name` and `files` follow `project.open`'s rules: the same limits, the same `dropped`, and the project folder starts empty (the previous project's files are removed first). The display settings are staged as for `project.open`, as `<stem>.kicad_prl` beside the file KiCad loads the project for: the source board, or a schematic's converted root (below). KiCad's importers leave pours unfilled; once the reader fills them (`B`, Fill All Zones), they draw opaque.
- In a `pcb` frame `open` names the foreign board among `files`. It must end, in any case and after a non-empty name, with one of `.brd` (Eagle or Allegro; the engine tells them apart by content), `.cpa` (CADSTAR), `.json` (EasyEDA Std), `.zip` (EasyEDA Std or Pro), `.asc` (PADS ASCII), `.pcb` (P-CAD or gEDA; the engine tells them apart by content), `.txt` or `.fab` (Fabmaster), `.pcbdoc` (Altium Designer), `.cmpcbdoc` (Altium Circuit Maker), `.cspcbdoc` (Altium Circuit Studio) or `.swpcbdoc` (SolidWorks PCB), or the request answers `bad_args`; `sheets` or `project` in a `pcb` frame answer `bad_args`. The frame opens it through the engine's own open (`kicadOpenFile`).
- In a `sch` frame `open` names the foreign schematic among `files`. It must end, in any case and after a non-empty name, with one of `.schdoc` (Altium), `.sch` (Eagle), `.csa` (CADSTAR), `.asc` (LTspice), `.json` (EasyEDA Std) or `.zip` (EasyEDA Pro), or the request answers `bad_args`. The frame runs KiCad's own schematic import (`kicadImportSchematic`, KiCad's File > Import path) with the importer its extension names, as KiCad's own type string: `Altium`, `EAGLE`, `CADSTAR Schematic Archive`, `LTspice`, `EasyEDA (JLCEDA) Std`, `EasyEDA (JLCEDA) Pro`. Only Altium is tested; the other schematic kinds are configure-confident, untested: the engine compiles their importers and the island routes them by extension, but no e2e has opened one. A gEDA `.sch` is read as Eagle (the island picks the importer by extension), and PADS Logic is not routed.
- An Altium project, in a `sch` frame: `sheets` lists every `.schdoc` of the project among `files` (a non-empty list of at most 4096 strings, each ending `.schdoc`) and `project` names its `.prjpcb`. Both come together or not at all, and `open` must be one of `sheets`, or the request answers `bad_args`; the frame checks `open` but does not pass it on: KiCad's project import is given every sheet and keeps the project's documents as top-level sheets, the first being the `sch0` document's (measured below). A sheet or a project file that was not written answers `open_failed`, its `message` naming it. The frame runs KiCad's project import, `kicadImportSchematic("", "Altium", props)`, `props` a JSON object of `project_file` (the project file's absolute path in the project folder) and `sch0`, `sch1`, ... (every sheet's absolute path, each once, in code point order, the order KiCad's own project import lists them in).
- In a `sch` frame the import is two steps. KiCad's schematic import names the converted root after the project the editor has loaded, and a fresh frame has none, so the frame first writes KiCad's empty sheet at the target (below; a staged file of that name is replaced) and opens it through `project.open`'s own open, which loads `<target stem>.kicad_pro` beside it: the host stages that file among `files` (an Altium project's is named after the `.prjpcb`); without one KiCad starts from its defaults, as a board's open does. Then it runs the import, which replaces the empty sheet. If that open does not settle within the import's time limit, or settles with a load or a KiCad dialog still holding it, the import answers `open_failed` naming the target, imports nothing and leaves the dialog for the host's reload of the frame.
- `open` must be one of the written files, or the import answers `open_failed`. `format`, when given, is a string of at most 64 characters: a hint the island may ignore (today it does; the engine, or a schematic's extension, picks the importer).
- The frame answers the importer's own dialogs: the layer mapping (Eagle, CADSTAR, PADS boards) gets Auto-Match Layers, then OK; the log report the engine shows after some board imports gets OK; a schematic importer's issues report (a lone OK under the title "Report" or under an HTML box, which holds its lines; shown when the importer reported anything) gets OK; the schematic import's progress dialogs (a gauge and Cancel: "Load Schematic" for the empty sheet's open, then the import's own) are left alone, as a board's ("Load PCB") is; the frame knows a progress dialog by those parts, never by its title. A "Report" box during a board import is any other dialog. In a schematic import KiCad's error box ("Error", raised by a load error or an exception, with or without a details pane) fails the import with `import_failed`, its `message` naming it and carrying its text; a board import keeps its earlier rule (an error box with a details pane is read as a log report, so the refusal's `message` ends with its first line). Any other dialog fails the import the same way, and is closed without accepting anything it asks (its Cancel, No or Close, else a lone OK, else its close box; never Save or Discard). A file the engine refuses answers `import_failed` too; a schematic import counts as refused unless a converted sheet holds anything. No dialog is left up when the import answers, unless one refused to close past the time limit (below).
- A converted board is then saved through the engine as `<stem>.kicad_pcb` beside the source (`boards/aht20.brd` becomes `boards/aht20.kicad_pcb`; a staged file of that name is replaced). It arrives as `ev.saved` before the answer, and `opened` names it. A save that writes nothing answers `import_failed`.
- A converted schematic is saved through the frame's own Save, KiCad's Save as `project.save` runs it in a `sch` frame: its root as `<stem>.kicad_sch` beside the source (`sheets/core.SchDoc` becomes `sheets/core.kicad_sch`), an Altium project's documents as top-level sheets in the project folder beside the `.prjpcb`, with no wrapper sheet above them: KiCad names the first top-level sheet's file (the `sch0` document's) after the project, `<project stem>.kicad_sch`, so that document gets no `<sheet stem>.kicad_sch`, and saves every other document as `<sheet stem>.kicad_sch`; the `.kicad_pro` lists them all in `schematic.top_level_sheets`, the only place that ties them together (below). Every sheet file and the `.kicad_pro` arrive as `ev.saved` before the answer, and `opened` names the root: the source's `<stem>.kicad_sch`, or an Altium project's `<project stem>.kicad_sch`. A save that writes nothing, or not the root, answers `import_failed`.
- `warnings` are the lines of the engine's log report: what its importer logged (its debug lines left out), each line once, in order, whitespace folded, at most 40 lines of at most 200 characters each; `[]` when it logged nothing. They are KiCad's own English sentences, as its report shows them, with one exception: a schematic importer's issues report draws its lines on a canvas, so its own sentences are not readable from the frame, and when it showed, `warnings` starts with the island's own line "KiCad reported issues while importing the schematic; the converted sheets may be incomplete."
- `chrome` is as for `project.open`: the hidden chrome is put back once after the save, and `chrome` says what is visible then. No answer waits for a watch (island `v0.2.3-cc22`; before it the import answered about 1.5 s later for one). For an engine that does not hold its own chrome the watch runs from the save on, behind the fit below and the answer.
- Then the frame fits the converted document itself: once the drawing's size (and the surface the engine draws into) has held for about 0.3 s, it presses Zoom to Fit (`Home`), and it answers once the drawing is painted (the view holds, and two small readbacks of the drawing in a row agree and show more than one color). A size that changes meanwhile starts the fit over. Past about 10 s it answers all the same, and the fit is made once the size holds (see `view.fit`). From the answer on, the fit holds as after a `view.fit`.
- The whole import, from the open to the save, is bounded by about 60 s. Past it, the frame cancels the load, closes every dialog (and any its canceling raised), then answers `import_failed`; if a dialog is still up about 5 s later, the `message` ends "a dialog stayed up", and the host reloads the frame. A schematic's save must start within that bound, and is then bounded by the save's own limits (`project.save`). After a failed import the frame settles KiCad's chrome as after a failed `project.open`; with the engine still parked in a load that call waits its own 30 s, so such an answer can come about 100 s after the request (measured: 99 s Chromium, 101 s Firefox). An import whose engine call traps (a WebAssembly `RuntimeError`, which unwinds KiCad's load without its cleanup and leaves the engine busy for good) waits for none of that: it answers `import_failed` "the engine stopped: " and the engine's error at once, touching no dialog and calling the engine no more, and every later request but `shutdown` and the library reads answers `not_ready` "the engine stopped". An import trap sends no `ev.state` `fatal` (the frame shows its fatal screen quietly): the answer and the `not_ready` that follow tell the host everything, so a host in the middle of a hand-off (an Altium project's board step, then its schematic step in a rebooted frame) is not interrupted; the host closes or reboots the frame on its own (measured 2026-10-16 with engine run 4, whose Altium board loads trap: 0.47 s from the request to the answer, Chromium and Firefox alike, where it was 99 s; Firefox's error reads "RuntimeError: unreachable executed").

### project.save
Saves the project through the engine's own Save and answers once every file it wrote has arrived as `ev.saved`; the answer is never sent before them.

- In a `sch` frame it is KiCad's Save, the same path as Ctrl+S in the editor: every sheet file of the hierarchy and the project file (`.kicad_pro`), whichever sheet the editor is showing and whichever sheets hold edits. The frame waits until every sheet file the engine's sheet tree names (and the root's `.kicad_pro`, when one was staged) has arrived, then a short pause with nothing more; without a sheet tree, until about 2 s pass with nothing more.
- In a `pcb` frame it is the board: the board file the frame opened.

`saved` lists the project-relative paths written, in the order they arrived, each once; `path` names the document the editor is showing (in a schematic, the file of the sheet on screen; the opened file when that sheet is outside the project), kept for hosts older than `saved`. Only bytes the engine itself wrote count: when it writes nothing (in a `sch` frame, no file within about 8 s), the request answers `save_failed` and, in a `pcb` frame, the file keeps its previous bytes. In a `sch` frame the save is a key press. A popup menu (a context menu, KiCad's clarify-selection menu) holds no edits, so the frame first closes it as a press of Escape does and then saves; it answers `busy`, and nothing is pressed, while a dialog is up (as for `key.press`) or a menu bar popup is open (it takes no Escape).

A host applies every `ev.saved` to its copy of the project, and resolves its save on the answer, never on the first `ev.saved`. An answer without `saved` comes from an older island: what it wrote is unknown, and only the answer says the save is over.

### project.forget
Drops the document: the project folder is emptied, and from then on the frame emits no `ev.saved` (a Ctrl+S in the document KiCad still shows is not reported) until the next successful `project.open`. The host reloads or removes the frame afterwards. The answer is `{}`; if emptying the folder fails it is `island_error`, and the document is dropped all the same.

### project.write
Writes text files into the running engine's project folder, each at `<project folder>/<path>` (UTF-8), creating its folders as `project.open` does and replacing a file that is there (island `v0.2.3-cc10`; a host gates it on `ev.ready` `caps` listing `write`, below; an older island answers `unknown_op`). It is how a page that keeps two frames booted at once, a `sch` frame and a `pcb` frame of the same project, hands one frame's saved files to the other without rebooting it: each frame has its own copy of the project folder.

- The answer `{ written }` comes once every file's bytes are in the folder: the paths written, in the order sent, each once (a path sent twice is written twice, in order, so its last text stands).
- The engine is never told. KiCad reads a written file the next time it opens it: a board's Update PCB from Schematic, a sheet opened again, a project loaded again. In a `pcb` frame the engine's Update PCB from Schematic opens the schematic again from the folder on every run (the root `<project name>.kicad_sch` beside the board, the project being the board's), so the sheets written there are what the next update reads (read from the engine's KiCad source, `PCB_EDIT_FRAME::TestStandalone` under `__EMSCRIPTEN__`; not measured). A file the engine holds in memory is not read again until then, and one it writes from memory on its own save is written over by that save: KiCad keeps the loaded project's settings in memory and writes the `.kicad_pro` from them when it saves it (KiCad's `JSON_SETTINGS::SaveToFile`; measured 2026-10-21 on Glasgow in a `sch` frame: a `glasgow.kicad_pro` written with one key added, then `project.save`, and the `.kicad_pro` KiCad saved, 17,179 bytes, did not hold the key).
- No document is needed: the folder exists from boot on. A later `project.open` or `project.import` empties it first, as always, and `project.forget` empties it.
- A write is never a save: it emits no `ev.saved` and no `ev.edited`, and a written file is reported as `ev.saved` only when the engine itself saves it later.
- `files` holds 1 to 4096 entries, each exactly `{ path, text }`. `path` follows `project.open`'s rules and must already be in their normal form (relative, POSIX, no `.` or `..` segment, no empty segment, no leading slash, no backslash, no NUL, at most 255 bytes in UTF-8), so `written` names the paths as sent. `text` is a string. The texts together are at most 32 MiB (33,554,432 bytes) of UTF-8. Anything else answers `bad_args`.
- The frame refuses every file of the document kind it holds, in any case, with `open_document` (`message` names the first such path): every `.kicad_sch` in a `sch` frame, which holds the whole sheet hierarchy, and every `.kicad_pcb` in a `pcb` frame. Everything else is taken: `.kicad_pro`, `.kicad_prl`, `fp-lib-table`, `sym-lib-table`, `.kicad_sym`, `.pretty/*.kicad_mod`, and the other frame's document kind.
- A path that names a folder, or runs through a file (on disk or earlier in the same request), answers `bad_args`, its `message` naming it.
- The checks, in order: the args (`bad_args`), the frame's own documents (`open_document`), the engine (`not_ready` before `ev.ready`), the folder (`bad_args`). Every check runs before the first byte is written, so a refused request writes nothing. A failure the checks cannot foresee (the file system out of memory) answers `island_error`, the files before the failing one written.
- It waits in the request queue like any request, so it never lands inside a `project.save` sent before it; while a `project.import` runs it answers `busy`.
- Measured 2026-10-21 on the local pair (Chromium, the GPU window, Glasgow open): a 1 MiB text answers 5.8 to 7.8 ms after the host's post (the first write of a page 21.6 ms), a refused request 0.2 ms. Two frames of one origin on one page, a `sch` frame with Glasgow open and a `pcb` frame booted beside it, each answered `project.write` (the second booted in 1.6 to 1.7 s from the browser's cache), and the first still answered `project.write`, `sheet.tree` and `project.save` after the second's `shutdown` and removal. Nothing of the island assumes one frame per origin: no lock, broadcast channel, shared worker, origin private file system or service worker; the library cache is IndexedDB `cc-libs` (version 1, the store created only when missing, entries keyed by the library tag and read far more than written, so two frames only ever write the same bytes under the same key), and the engine's wx configuration in `localStorage` held no key after boot.

### chrome.show and readonly
`chrome.show { on }` turns KiCad's own window chrome on or off (the engine's `kicadSetChrome`); `readonly { on }` turns read-only mode on or off (`kicadSetReadOnly`). Each answers `{}` only when the engine confirms the change, else `not_applied`.

The frame boots with KiCad's chrome hidden (`kicadSetChrome(false)`); `chrome.show { on: true }` brings it back for that boot only. Loading a file shows KiCad's menu bar again (and an infobar for a file from an older KiCad), so while the chrome is hidden each `project.open` that reached the load (`open_failed` included) hides it again before it answers; the successful answer's `chrome` says whether that hide held (see `project.open` for what follows the answer).

### key.press
Fires one KiCad hotkey: the frame dispatches a `keydown` and then a `keyup` carrying `key`, `code` and the three modifiers on its window, where KiCad reads its hotkeys, and answers `{}`. KiCad's place keys are the exception when `ev.ready` listed `picker` (see `ev.pick`): a `key.press` of `a` (or `A`), and of `p` in a `sch` frame, with no modifier, while nothing of KiCad's own is over its canvas, presses nothing, emits `ev.pick` and answers `{}`. A key may zoom, pan or start a tool, so it ends a fit that was holding (see `view.fit`). Keyboard focus is put on the drawing once at boot, so the first key is not lost; the op itself never clicks. `code` is one of `KeyA` to `KeyZ`, `Digit0` to `Digit9`, `F1` to `F12`, `Escape`, `Home`, `Delete`, `Backspace`, `Enter` or `Space`; `key` is one character, or one of `F1` to `F12`, `Escape`, `Home`, `Delete`, `Backspace` or `Enter`; each modifier, when given, is a boolean (absent means not held). Anything else answers `bad_args`. While a popup menu (a context menu, KiCad's clarify-selection menu) or a dialog (any wx type whose name contains `Dialog`, except a progress dialog) is up, the key is refused with `busy` rather than landing in it. A progress dialog is a wx type whose name contains `Progress`, or a dialog that shows a gauge and no button but Cancel (or Skip), as KiCad's own progress reporter does; it takes no keys.

A real press anywhere in the frame (a pointer down, or a touch's pointer up) gives the frame the browser's keyboard focus when it does not have it, so the user's own keys reach KiCad and not the host page; this also blurs the host's window. The boot's own focus click never takes the browser's focus.

### view.fit
Fits the drawing to the view: the frame presses KiCad's Zoom to Fit hotkey (`Home`) exactly as `key.press { key: "Home", code: "Home" }` would, and answers `{}`. While a popup menu or a dialog is up (as for `key.press`) it answers `busy` and nothing is pressed.

The fit then holds. KiCad keeps its scale when the drawing is resized, so while it holds the frame watches the drawing's size and the surface the engine draws into (the largest GL canvas wx.js shows, or the root canvas the engine's software renderer draws into once its GL canvas is gone, as after a lost GPU process). Once either has changed and held for about 0.3 s, with no popup menu or dialog up, the frame presses `Home` again. A `view.fit` while the fit holds at the same size presses nothing (the view is already fitted; on a software GPU a repaint of a large board took seconds). The fit stops holding when the reader steers: a real wheel, pointer press or key in the frame, or any `key.press` from the host. `project.open`, `project.import` and `project.forget` end it too; a successful `project.import` starts it again with its own fit.

### sheet.tree and sheet.enter
`sheet.tree` answers the schematic's sheet hierarchy as the engine reports it. `current` is the path of the sheet the editor is showing. Each row of `sheets` carries the sheet's `path` (`/` for the root, then one lower case UUID and a slash per level), its `name`, its page number as a string (`page`), its `depth` below the root, the path of its `parent` (empty for the root) and the base name of its file (`file`, for example `io_banks.kicad_sch`; never a path, and empty when the engine gives none). A row the engine reports without a string `path` or `name` is left out. A schematic of several top-level sheets (an Altium project's import, `project.import`) reports each of them at the path `/`, depth 0, with an empty `parent`, told apart only by `name`, `page` and `file`. `currentFile` (island `v0.2.3-cc8`) is the base name of the file of the sheet the editor is showing, which tells such sheets apart where `current` cannot: the frame takes the root's when a document opens or is imported (KiCad shows it first), then each sheet KiCad reports showing, whoever switched it (`sheet.enter`, or the reader in the editor); it is empty while no document is open. In a `pcb` frame the engine has no sheet tree and the request answers `unsupported`.

`sheet.enter { path }` shows the sheet at `path`. `path` must match `/` followed by zero or more `<uuid>/` segments, the UUIDs in lower case hexadecimal (`8-4-4-4-12` digits), or the request answers `bad_args`. The answer is `{}` when the engine accepts the path, else `not_applied` (an unknown sheet, or no answer within 30 s). The editor switches sheets shortly after the answer: a host that needs to see the change polls `sheet.tree` until `current` follows.

`file` (island `v0.2.3-cc8`; an older island answers `bad_args` to it), when given, picks among the sheets at `path` the one whose `file` in `sheet.tree` it equals: the base name of a `.kicad_sch` file, exactly as `sheet.tree` reports it. A `file` of any other shape, or one no sheet at `path` holds, answers `bad_args`; a `path` no sheet has answers `not_applied`. KiCad 10 reports every top-level sheet at `/` and the engine's own enter reaches only the first of them, so the frame enters `path`, then presses KiCad's Next Sheet (`PgDn`, which goes by page through every sheet of the schematic, the sheets below included) until KiCad reports showing that file at `path`, at most one press per row of `sheet.tree`. The answer comes once KiCad shows it: `{}` (at once, pressing nothing, when it already does), `busy` (nothing pressed further) while a dialog or a popup menu is up, else `not_applied` when KiCad does not report a switch within about 5 s of a step (measured: each switch is reported 50 to 125 ms after the enter or the key, and the eDP adapter's second sheet was shown 100 to 180 ms after the request).

The walk is visible and is not undone:
- Each step shows a sheet on the way to the one asked for: the first sheet at `path` after the enter, then each sheet Next Sheet passes. A `busy` or a `not_applied` partway through leaves the sheet of that step on screen; the host enters again, or reads `sheet.tree` `currentFile` to see where the editor is.
- Each step adds an entry to KiCad's back history (Navigate Back, `Alt+Left`), so the reader's Back goes through the sheets the walk passed.
- Two sheets at the same `path` with the same `file` cannot be told apart: when one of them is shown, the request answers `{}` at once, and otherwise the walk stops at the first of them it reaches.
- The clean fix is an engine export that enters a sheet by its path and its file (`kicadSheetsEnter(path, file)`), with the shown sheet's file in the engine's sheet tree. It is not built; until it is, `file` takes the walk above.

### layers.get, layers.visible and layers.active
`layers.get` answers the board's layers as the engine reports them: `active` is the id of the active layer, and each row of `layers` carries the layer's `id` (an integer `0` to `127`), its `name` as the board names it, its `canonical` KiCad name (for example `F.Cu`), its `color` as a CSS color string (empty when the engine gives none), whether it is `visible`, and whether it is a `copper` layer. A row without a valid `id`, a string `name` or a string `canonical` is left out. In a `sch` frame the engine has no layers and the request answers `unsupported`.

`layers.visible { id, visible }` shows or hides a layer, and `layers.active { id }` makes a layer the active one. `id` is an integer `0` to `127` and `visible` a boolean, or the request answers `bad_args`. Each answers `{}` when the engine confirms the change, else `not_applied` (a layer the board does not have, or no answer within 30 s). The engine applies the change shortly after it answers.

### lib.index, lib.item and lib.prefetch
The fast part picker's library reads (the host's picker, `PICKER.md`). They read KiCad's library mirror on the island origin (`LIBRARY.md`) and never ask the engine to enumerate a library. Either kind is read in either frame (a `sch` frame answers footprint reads too). Each is answered outside the request queue (above), a running `project.import` included, and before `ev.ready` answers `not_ready`.

- `kind` is `symbol` or `footprint`. `lib` is a library's nickname as a lib table names it (`Device`, `Package_QFP`), `name` an item's name; each is a string of 1 to 255 characters with no control character. `libs` is an array of at most 16 such nicknames. Anything else, or any other key, answers `bad_args`.
- `lib.index { kind }` answers the mirror's search index of that kind (`sym-index.json` or `fp-search.json`, `LIBRARY.md`) as its JSON text, the same bytes on every answer of a session; `text` is null when the island has no mirror (it booted on its example library) or the mirror has no index.
- `lib.item { kind, lib, name }` answers the item's body: for a symbol a self-contained `kicad_symbol_lib` holding the symbol and, for a derived one, its `extends` chain root first; for a footprint the `.kicad_mod` text. `body` is null when the library or the item is not there. The first read of a library fetches its bundle (a few hundred milliseconds cold; afterwards it is read from the browser's storage).
- `lib.prefetch { kind, libs }` answers `{}` at once and warms the named libraries' bundles in the background at low priority, each once; a nickname the mirror lacks is passed over, and without a mirror nothing is warmed.

### place
Puts a library item on the pointer, as KiCad's own chooser would after a pick: the item follows the pointer, KiCad's keys act on it (R rotates it), a press in the drawing commits it (one undo step, then an `ev.edited`) and Escape drops it. The answer `{}` comes once the item hangs off the pointer.

- The args are `lib.item`'s and four optional strings, `value` and `footprint` (island `v0.2.3-cc11`, the `fields` cap below) and `mpn` and `manufacturer` (island `v0.2.3-cc11`, the `identity` cap below), each 1 to 200 characters with no control character; a footprint takes `value` alone. The checks, in order: the args (`bad_args`, a footprint's `footprint`, `mpn` or `manufacturer` among them, before the frame's kind is read); the frame's kind and the engine (`unsupported`: a symbol in a `pcb` frame, a footprint in a `sch` frame, or an engine without `kicadPlaceImportedItem` or `kicadCollabGetSelection`, which `message` names); an engine up with a document opened by `project.open` or `project.import` (`not_ready`); no load parked, no popup menu and no dialog up, as for `key.press` (`busy`, nothing changed); the item (`not_found`, `message` naming `lib:name`).
- The frame builds the editor's clipboard text from the body and hands it to the engine's `kicadPlaceImportedItem`. A symbol is placed as `lib:name` (its lib table's nickname, so it resolves against the project's libraries as a chooser pick does), its definition cached in the sheet's `lib_symbols` flattened (a derived symbol carries its parents' graphics and pins under its own name, its fields merged as KiCad's own flatten merges them) and its instance carrying the library's fields at their library positions; KiCad annotates it (`R1`, `#PWR01`). `value` and `footprint` are written on that instance's Value and Footprint fields (at the library field's position, with its effects; a body with no Footprint field gets one, hidden), never on the definition in `lib_symbols`, which keeps the library's own; an absent one leaves the library's. `mpn` and `manufacturer` are written on that instance as the fields `MPN` and `Manufacturer`, hidden, after the library's fields (over a library field of that name when there is one), never on the definition. A footprint is placed as `lib:name` with its pads on no net, and `value` replaces its Value text (a body with none gets one on F.Fab).
- The answer waits until the editor holds the item (its selection names a new item): `busy` when the engine reports a load in flight or never takes the item within about 10 s (a placement of KiCad's own already under way), `island_error` when it refuses the text it was given.
- One item at a time: a `place` while the previous one still hangs off the pointer drops that one first, as Escape would. When the reader drops a schematic item with Escape (or Undo), the frame also leaves KiCad's placement tool, whose next press in the drawing would otherwise open KiCad's own chooser.
- Keyboard focus stays where it is: after the answer, the host gives the frame the focus (`iframe.focus()`) when the reader should be able to rotate the item before the press.
- A host uses `place` (and opens its picker on `ev.pick`) only when `ev.ready` `caps` lists `picker`. The pinned engine has had `kicadPlaceImportedItem` since PCBJam v0.2.3, so an older island lists that export too and answers `unknown_op`; `picker` is the island's own word. `place` still answers on the example library (it is not refused without the cap), but no `ev.pick` is sent there. A host sends `value` and `footprint` only when `caps` lists `fields`, and `mpn` and `manufacturer` only when it lists `identity`: an older island's `place` answers `bad_args` to them.

### select
Selects items in the editor, as a press on them would (island `v0.2.3-cc9`; a host gates it on `ev.ready` `caps` listing `selection`, below; an older island answers `unknown_op`). The selection becomes exactly the items found: the frame clears the editor's selection, then hands each id to the engine's own select by uuid (`kicadCollabTestSelectByUuid`, which finds a board item anywhere on the board and a schematic item among the shown sheet's items, and adds it to KiCad's selection), and answers `{}` once the editor's selection holds exactly the items it found. An id the editor does not hold (a part placed since the host's copy was saved, an item of another sheet) selects nothing and is no failure: `select { uuids: [] }` clears the selection.

- `uuids` lists item uuids (symbols, footprints, wires, tracks, anything KiCad selects) and `fpPaths` footprint paths, `/<sheet uuid>/.../<symbol uuid>`, as `ev.selected` carries them; each list holds at most 4096 entries, every uuid in KiCad's own lower case spelling (`8-4-4-4-12` hexadecimal digits), and a repeat counts once. `zoom`, when true, fits the view to the items found afterwards through KiCad's Zoom to Selected Objects (seeded on Ctrl+Shift+Home, a key no KiCad action takes; nothing is pressed when nothing was found). Any other key, a list of another shape, or a `zoom` that is not a boolean answers `bad_args`.
- In a `sch` frame each footprint path selects its symbol (the path's last uuid), as KiCad's cross-probe does; a reused sheet's symbols share their uuids across its instances, so the symbol is selected on the sheet shown. In a `pcb` frame `fpPaths` selects nothing: the engine has no export that finds a footprint by its path, so a host selects a footprint by its own uuid there.
- The checks, in order: the args (`bad_args`); the engine (`not_ready` before `ev.ready`; `unsupported` without `kicadCollabTestClearSelection`, `kicadCollabTestSelectByUuid` or `kicadCollabGetSelection`, which `message` names); a document opened by `project.open` or `project.import` (`not_ready`); no load parked, no popup menu and no dialog up, as for `key.press`, and no item placed by `place` hanging off the pointer (`busy`, nothing changed). The answer is `not_applied` (nothing zoomed) when the editor refuses the clear or does not hold the selection within about 2 s.
- A zoom steers the view: a fit that was holding ends (see `view.fit`). The selection the request made reaches the host as `ev.selected` like any other.

### project.libs
Registers libraries of the project folder, the design's own (island `v0.2.3-cc12`; a host gates it on `ev.ready` `caps` listing `projectLibs`, below; an older island answers `unknown_op`), so that KiCad finds their items without a reboot: its own chooser lists them, a footprint loads by its `lib:name`, Update PCB from Schematic finds a symbol's footprint there, and the island's `lib.item` and `place` read them. It is how a page adds a part the reader brought from another library to a running editor: it writes the library's files and the project's lib tables into each frame through `project.write`, then sends `project.libs` naming the library.

- `libs` lists 1 to 16 library nicknames, each a string of 1 to 255 characters with no control character and none of `/`, `\` and `:` (the nickname is the tail of the engine's library uri, and KiCad's `lib:name` splits on the colon); a repeat counts once. Anything else, or any other key, answers `bad_args`.
- `${KIPRJMOD}` is the project's folder as KiCad has it: the folder of the document the frame opened (`project.open`'s `opened`, or an import's converted document), since KiCad loads the project named after the file it opens, beside it; while no document is open, the project folder's root. A design whose project file sits in a subfolder (`Hardware/Main-board/keyboard.kicad_pro`) has its tables and its library there, as KiCad writes them.
- A nickname is a project library when the project's own lib table in `${KIPRJMOD}` names it in a row of type `KiCad` whose uri is `${KIPRJMOD}/` and a path in `project.open`'s normal form: in `sym-lib-table` a path ending `.kicad_sym` that names a file there, in `fp-lib-table` a path ending `.pretty` that names a folder there. Tables elsewhere in the folder (its root, when the project sits in a subfolder) are not read. The tables are KiCad's own s-expression (`(sym_lib_table (version 7) (lib (name "...") (type "KiCad") (uri "${KIPRJMOD}/...") (options "") (descr "")))`), as KiCad writes them; the frame reads them as KiCad does (any row order, any other rows). A nickname named in both tables is registered as both kinds. For a design whose stem is `glasgow`, its project file at the folder's root:
  ```
  glasgow_parts.kicad_sym                        the symbols
  glasgow_parts.pretty/<footprint>.kicad_mod     one file per footprint
  sym-lib-table   (lib (name "glasgow_parts")(type "KiCad")(uri "${KIPRJMOD}/glasgow_parts.kicad_sym")(options "")(descr ""))
  fp-lib-table    (lib (name "glasgow_parts")(type "KiCad")(uri "${KIPRJMOD}/glasgow_parts.pretty")(options "")(descr ""))
  ```
- The answer `{ symbol, footprint }` lists the nicknames registered as each kind, in the order sent; it comes once the engine has loaded every one of them (its apply queue idle).
- From the answer on, in this frame:
  - `lib.item` and `place` read a registered nickname's items from the project folder, never from the mirror: a symbol from the `.kicad_sym` file (a derived symbol with its `extends` chain from the same file, self-contained as `lib.item` gives a mirror's), a footprint from `<name>.kicad_mod` in the `.pretty` folder. `place` puts it down as `<nickname>:<name>`, as for a mirror library. `lib.index` and `lib.prefetch` are unchanged: the mirror's index holds no project library (the host builds its own rows from the files it holds) and a prefetch of a project nickname warms nothing.
  - KiCad reads them too: the frame adds a row of that nickname to the engine's library table at run time (the engine's `kicadLibsAddEntry`), served by the island from the project folder, and the engine loads it. KiCad's own symbol and footprint choosers list it, and Update PCB from Schematic, a footprint loaded by name and every other read of KiCad's find its items.
  - Every `project.libs` reads the folder again (the engine's `kicadLibsReload`): an item written since is found, one removed is gone. A host writes a new item, then sends `project.libs` again.
- A design opened with its project library among `project.open`'s files (the tables beside the project file) already has it: KiCad reads the project's own tables when it loads the project, and its native rows serve the items (measured below). Those rows take precedence in KiCad; `project.libs` on them refreshes them and gives `lib.item` and `place` their items. So the state after a reboot is the state after the op.
- A nickname the island already serves another way, a library of its mirror or of the example library, answers `bad_args` (`message` names it): KiCad keeps a library table row of that name from boot, and the engine's run time add keeps the existing row (measured: nothing of the project's library resolves under a mirror nickname). The host names its project library apart (`<stem>_parts`).
- A row added stays in the engine's table for the frame's life (the engine has no export to remove one), served from the project folder: after a later `project.open` empties the folder, a library whose file or folder is gone reads as empty. A reloaded frame starts with none, and a host registers again after it.
- No document is needed: the folder and the engine's tables exist from boot.
- The checks, in order, every one before any effect: the args (`bad_args`); the engine (`not_ready` before `ev.ready`; `unsupported` without `kicadLibsAddEntry`, `kicadLibsReload` or `kicadCollabBusy`, which `message` names); the tables (`not_found`, `message` naming the first nickname that is no project library above, `bad_args` for a nickname the island serves another way); a load parked, a popup menu or a dialog up, as for `key.press` (`busy`, nothing changed). Then the rows are added and loaded. Past about 10 s with the engine's apply queue still busy the answer is `island_error` (the rows are added; a later `project.libs` loads them again).
- It waits in the request queue like any request; while a `project.import` runs it answers `busy`.
- Why this road (spike, 2026-10-27, Chromium, the GPU window, the local pair, Glasgow in a `pcb` frame with the full mirror; the probe is the engine's own `kicadLibsTestLoadFootprint(nickname, name)`, which answers a loaded footprint's pads, else nothing):
  - KiCad's own reload over the project's tables (the engine's `kicadLibsReload` after `project.write` put the tables and the library in the folder) finds nothing on a live engine: the probe answered nothing before and after, the reload taking 407 ms. KiCad reads a project's lib tables once, when it loads the project (`LIBRARY_MANAGER::LoadProjectTables`, reached from no engine export), and the reload only refreshes a row its tables already hold. It works only after a reboot: with the tables and the library among `project.open`'s files the probe answered `1:800000x950000;2:800000x950000;` 8 ms after the open, and a footprint written into that `.pretty` folder after the open was found too (31 ms with a reload).

- The schematic is `<the opened board's folder>/<the board's stem>.kicad_sch` in the project folder (the board engine holds the sheets the host staged or wrote with `project.write`); `no_schematic` names that path when it is not there.
- `sheets` are the top-level sheet files the engine read, project paths in `project.open`'s form, in KiCad's order. `changes` are KiCad's changes as records, each with exactly its kind's keys: `add` (`ref`, `footprint`, `pins` (each `{ pin, net, pad }`, `pad` false when the footprint has no pad of that number), `extraPads`, `sameName`: a footprint of that designator is on the board already), `remove` (`ref`, `footprint`), `footprint` (`ref`, `from`, `to`), `reference` (`ref`, `to`), `value` (`ref`, `from`, `to`), `detail` (`ref`, `topic` one of `fields`, `link`, `sheet`, `filters`, `attribute`, `jumpers`, `group`, `class`, `units`, `variant`, `name`, `from`, `to`), `connect` (`ref`, `pin`, `to`), `reconnect` (`ref`, `pin`, `from`, `to`), `disconnect` (`ref`, `pin`, `from`), `net` and `unusedNet` (`net`), `copper` (`item` `via` or `zone`, `name`, `from`, `to`) and `problem` (`code` one of `no_footprint`, `footprint_not_found`, `footprint_without_library`, `locked`, `pad_without_pin`, `pin_without_pad`, `pins_unnumbered`, `via_unknown_net`, `zone_without_pads`, `variant_footprint`, `unannotated`, `duplicate_designator`, `duplicate_sheet_names`; `severity` `warning` or `error`; `ref`, `pin`, `footprint`, `net`, `name`), each with `message`, KiCad's own sentence for logs, never for display. A preview fills `pins`, `extraPads` and `sameName`; an update answers its new parts' connections as `connect` records and their designators in `added`. At most 4,096 records, past them `truncated: true` and the counts still total; `unmapped` counts KiCad's lines that no record carries (0 when every line is mapped). Strings are at most 1,024 characters.
- A preview of parts not numbered yet answers its list with `blocked: "not_annotated"` and the `unannotated` or `duplicate_designator` problems; `board.update` answers `not_annotated` then, and `stale` when the board or the schematic changed since the preview that gave the token. Both change nothing. `schematic_unreadable` when the engine could not read the schematic (`message` says why), or when a dialog came up while the run ran: it is closed without accepting anything it asks (its Cancel, No or Close, else a lone OK, else its close box) and `message` is its title.
- After an applied update the new parts sit beside the board's outline, selected, the whole update one undo step: an `ev.edited` and an `ev.selected` follow the answer. The engine never saves: the host's next `project.save`, or the reader's Ctrl+S, writes the board.
- The checks, in order, every one before any effect: the args (`bad_args`); the frame's kind (`unsupported` in a `sch` frame, "a board op runs in a pcb frame"); the engine (`not_ready` before `ev.ready`; `unsupported` without `kicadUpdateBoardFromSchematic` or `kicadCollabBusy`, which `message` names); a board opened by `project.open` or `project.import` (`not_ready`); a load parked, a popup menu or a dialog up, or an item placed by `place` hanging off the pointer (`busy`, nothing changed); the schematic (`no_schematic`). Then the engine's export runs the job on the editor's apply queue in a fresh folder `/tmp/cc-update/<n>/` (whatever an earlier run left under `/tmp/cc-update/` is removed first), writing its report and then its record, `.cc-update.json`, last; the frame answers once the apply queue is empty and the record is there, and removes the folder. `not_applied` when the engine refuses the run or its record has not come within 30 s.
- It waits in the request queue like any request; while a `project.import` or a `board.check` runs it answers `busy`.
- The run opens KiCad's schematic editor hidden, which takes wx's keyboard focus: after the answer the frame gives the drawing its focus back with a middle press near the canvas's corner (a middle press selects nothing), so the reader's keys and `key.press` reach KiCad again. After an applied update the frame reads the selection, since the engine selects the new parts with no selection emit: the `ev.selected` naming them follows the answer.
- Why an engine export (2026-11-10): KiCad's Update PCB from Schematic is a dialog the island never shows. So the engine gained `kicadUpdateBoardFromSchematic(argsJson)` (pcbjam `cc/main` 70fe8e2, bbdf4c6, e34d7a4 and 3dd83b2, with kicad `cc/main` 88eece91's change log of `BOARD_NETLIST_UPDATER`; engine run 12). An island on an engine without it lists no `boardUpdate` and answers `unsupported` naming the export.
- Measured over the local pair with engine run 12 built locally (2026-11-10, `tests/e2e/board-update.spec.ts`, with the library mirror served): first-board's preview 400 and 415 ms the first of a boot, then 11 to 36 ms (Chromium, then Firefox), the update 57 to 103 ms, its two parts beside the outline and selected, one undo step that Ctrl+Z takes back whole and Ctrl+Y brings again, the saved board holding both with their pads' nets; Glasgow's preview 871 and 799 ms first, then 189 to 249 ms, with 1,817 records and every line mapped. Without the library mirror each new part answers a `footprint_not_found` problem. An applied update reports KiCad's own lines for a new part beside its `add`: its designator from `REF**`, its value, its link to the symbol, its sheet and its footprint filters.

### board.check
KiCad's design rules check of the board with no KiCad dialog, as KiCad's Design Rules Checker does with the board's own severities, its findings answered as records (island `v0.2.3-cc19`, on an engine with `kicadCheckBoard`; a host gates it on `ev.ready` `caps` listing `drc`, below). The board engine checks the board it holds, unsaved edits included.

- The args are exactly `fill` (pour every copper area again first, as KiCad's dialog does by default), `parity` (compare the board with the schematic beside it) and `allTrackErrors` (list every problem along a track, not only its first), each a boolean. Anything else, or any other key, answers `bad_args`.
- The answer has exactly these keys: `violations`, `unconnected` (findings of type `unconnected_items`) and `parity` (the comparison's findings, KiCad's parity keys: `missing_footprint`, `extra_footprint`, `duplicate_footprints`, `net_conflict`, `footprint_symbol_mismatch`, `footprint_filters_mismatch`, `footprint_symbol_field_mismatch`), each a list of findings; `parityRun`, `yes` when the board was compared, `off` when not asked, `no_schematic` when no schematic sits beside it, `not_annotated` when its parts are not all numbered, `unreadable` when the schematic could not be read (the run goes on without the comparison); `filled`, whether the fill ran (engine run 12 pushes its undo step every time, even with nothing to pour: one undo step and an `ev.edited` after the answer, at the answer's `depth`); `skipped`, rule keys the run left out (at most 8); `ignored`, the rule keys the board's settings turn off (at most 128); `errors` and `warnings`, the findings NOT excluded of each severity, and `excludedCount`, the excluded ones, over all three lists, counted by the frame; `depth`, the undo depth after the run; and `truncated: true` when the lists were cut.
- A finding has exactly `marker` (the uuid of the mark KiCad left on the board; `board.explain` takes it), `type` (KiCad's rule key, `drc_item.cpp`: `clearance`, `unconnected_items`, `extra_footprint`, ...), `severity` (`error` or `warning`), `excluded` and `comment` (an exclusion the board's project file keeps, and its comment; excluded findings are listed), `layer` (a canonical layer name or `""`), `x` and `y` (the mark's position, millimeters), `items` (at most 64 listed), `rule` (`{ source, name }` when the test recorded the rule that raised it: `source` one of `board`, `netclass`, `custom`, `keepout`, `local`, `netTie`, `tuning`, `other`; else null), `actual` (millimeters, read from KiCad's message where it carries one, else null) and `message` (KiCad's sentence, for logs). An item has exactly `uuid`, `kind` (`pad`, `track`, `arc`, `via`, `zone`, `footprint`, `field`, `text`, `shape`, `outline`, `hole` or `other`), `ref` and `pad` (a pad's designator and number; `ref` also a footprint's, a field's and a footprint shape's), `net` (KiCad's net name), `layer`, `parent` (the footprint holding a pad, field or text, else `""`) and `description` (KiCad's English, for logs). At most 4,096 findings are listed, over the three lists in that order; the counts total all of them. KiCad's own words are cut at 1,024 characters.
- KiCad's marks stay on the board until the next check, and every check makes them anew: a mark's uuid holds until the next check, so `board.explain` takes the last check's marks. No undo step but the fill's; the marks change nothing the host saves. A mark cannot be selected by `select` (the engine's select by uuid takes no mark); the reader's double-click on one, or `E` with one selected, sends `ev.boardProperties` of kind `marker`. A pad's item has no `layer` (`""`): it lies on several.
- A check that compares the board with the schematic opens KiCad's schematic editor hidden, which takes wx's keyboard focus: after the answer the frame gives the drawing its focus back with a middle press near the canvas's corner, which selects nothing.
- Why an engine export (2026-11-10): KiCad's Design Rules Checker is a dialog the island never shows. So the engine gained `kicadCheckBoard(argsJson)`, KiCad's DRC job's body on the apply coroutine with the board's own rules compiled first (a rules file that does not compile stops the run), and `kicadExplainViolation(marker)`, `BOARD_INSPECTION_TOOL::InspectDRCError`'s evaluation answered as data (pcbjam `cc/main` 70fe8e2; engine run 12).
- Measured over the local pair with engine run 12 built locally (2026-11-10, `tests/e2e/board-check.spec.ts`): the drc-small fixture checked in 556 to 708 ms the first of a boot and 285 to 406 ms after, the fill, the comparison and every track error each changing it by less than 50 ms; its four findings exactly (the clearance against its custom rule `Tight`, 0.15 mm against 0.25 mm, the connection not made, R2 with no symbol, the excluded stub with its comment); ten checks in a row left the engine's memory at 369 MB; Glasgow checked once in 3.0 s (Chromium) and 5.0 s (Firefox) with the comparison, 429 violations and 421 differing (326 on run 12 rebuilt, island `v0.2.3-cc19`, 2026-11-10: 2.95 s in Chromium, 5.0 s in Firefox; the first build joined schematic connection points at (x, y) and (y, x) and listed 95 false net conflicts); a change sent during a check answered `busy`, a read answered. `board.explain` of the clearance mark answers in 9 to 12 ms (medians of 5, 10 and 11 ms).
- The checks, in order, every one before any effect: as for `board.preview` without its schematic (the args, the frame's kind, the engine with `kicadCheckBoard` and `kicadCollabBusy`, a board, busy). Then the engine's export runs in a fresh folder `/tmp/cc-drc/<n>/` (an earlier run's removed first), writing its report and then its record, `.cc-drc.json`, last; the frame answers once the apply queue is empty and the record is there, and removes the folder. `rules_invalid` when the board's custom rules file does not compile (`message` KiCad's parse message), with no check run; `island_error` when the report is of another shape, or when a dialog came up while the run ran (closed without accepting anything, as for `board.preview`; `message` is its title); `not_applied` when the engine refuses the run or its record has not come within 60 s.
- The check holds the editor for its run: it runs off the request queue, and until it is answered every request that would change the document, its view or the editor's state answers `busy` at once (everything but `board.item.get`, `board.explain`, `layers.get`, `shutdown` and the library reads, which are answered as usual, once the editor is free).

### board.explain
The rule behind one finding of the last `board.check`, as KiCad's own "Show DRC rule" works it out, read with no KiCad window (island `v0.2.3-cc19`, on an engine with `kicadExplainViolation`; a host gates it on `ev.ready` `caps` listing `explain`). The args are exactly `{ marker }`, a mark's uuid in KiCad's lower case spelling.

- The answer has exactly `constraint` (`clearance`, `hole_clearance`, `hole_to_hole`, `edge_clearance`, `track_width`, `track_angle`, `track_segment_length`, `connection_width`, `via_diameter`, `annular_width`, `hole_size`, `text_height`, `text_thickness`, `max_uncoupled` or `assertion`), `unit` (`deg` for `track_angle`, `mm` for every other constraint), `min`, `opt` and `max` (numbers or null), `source` and `name` (as a finding's `rule`; `name` is `""` for the board's own settings), `condition` (a custom rule's condition as its file writes it, else `""`; at most 2,048 characters), `layer` and `items` (0 to 2, each `{ uuid, netclass }`, the net class each item is in).
- KiCad explains sixteen rule keys: `clearance`, `hole_clearance`, `hole_to_hole`, `copper_edge_clearance`, `track_width`, `track_angle`, `track_segment_length`, `connection_width`, `via_diameter`, `annular_width`, `drill_out_of_range`, `microvia_drill_out_of_range`, `text_height`, `text_thickness`, `diff_pair_uncoupled_length_too_long`, `assertion_failure`. A mark of any other key answers `no_rule`; a board whose custom rules do not compile answers `rules_invalid`; no mark of the board with that uuid answers `not_found` (`message` the uuid).
- The checks, in order, as for `board.check` (the engine with `kicadExplainViolation`). It is a read: while a `board.check` runs it is answered once the editor is free.

### board.item.get and board.item.set
Read and change one board item's properties by uuid with no KiCad dialog (island `v0.2.3-cc19`, on an engine with `kicadBoardItemGet` and `kicadBoardItemSet`; a host gates both on `ev.ready` `caps` listing `boardItem`). They read the board the editor holds, unsaved edits included.

- `board.item.get` takes 1 to 512 uuids in KiCad's lower case spelling and answers the items the board holds, in the order asked (a uuid it does not hold is left out, so an empty list says the items are gone; a uuid asked twice is asked once, and an answer never names a uuid twice). A field or a text of a footprint answers its footprint, once. Each item has exactly its kind's keys: a footprint `{ kind: "footprint", uuid, locked, ref, value, libId, side ("front" or "back"), x, y, rotation (degrees, over -180 to 180), inBom, inPos, dnp, boardOnly, variant, symbolPath }`; a track or an arc `{ kind, uuid, locked, net, layer, width, length }`; a via `{ kind: "via", uuid, locked, net, x, y, diameter, drill, viaType ("through", "blind", "buried" or "micro"), top, bottom }`; a copper area `{ kind: "zone", uuid, locked, name, net, layers, priority, clearance, minWidth, padConnection ("thermal", "solid", "none" or "thtThermal"), thermalGap, spokeWidth, netChoices (every net of the board) }`; a board text `{ kind: "text", uuid, locked, text, layer, x, y, rotation, height, width, thickness, bold, italic, knockout, mirrored, hAlign ("left", "center" or "right") }`; anything else `{ kind: "other", uuid, type }`, `type` one of `pad`, `shape`, `dimension`, `textbox`, `table`, `group`, `image`, `barcode`, `rulearea`, `marker`, `other`. Lengths and positions are millimeters; layers are KiCad's canonical names (`F.Cu`, `In1.Cu`, `User.1`: letters, digits, dots and underscores, 1 to 32 characters), never a layer's name as the board renamed it, as `layers.get`'s `canonical`; a `net` of `""` is no net; a text is 1 to 4,096 characters and may hold line breaks.
- `board.item.set` takes exactly `uuid` and `set`, which holds exactly ONE key: `x`, `y` (at most 50,000 in magnitude), `rotation` (-360 to 360), `locked`, `side`, `inBom`, `inPos`, `dnp`, `ref` (1 to 64 characters, no control character), `value` or `name` (at most 1,024, no control character), `width`, `diameter`, `drill`, `clearance`, `minWidth`, `thermalGap`, `spokeWidth`, `height`, `thickness` (0.001 to 1,000), `layer`, `net`, `priority` (a whole number, 0 to 1,000,000), `padConnection`, `text` (1 to 4,096, line breaks and tabs allowed), `bold`, `italic`, `knockout`, `hAlign`. Each kind takes its own keys: a footprint `x`, `y`, `rotation`, `locked`, `side`, `inBom`, `inPos`, `dnp`, and `ref` and `value` only when it is board only (else it takes them from the schematic); a track or an arc `width`, `layer` (a copper layer) and `locked`; a via `x`, `y`, `locked`, `diameter` and `drill` (the hole smaller than the via); a copper area `name`, `net` (one of its `netChoices`, or `""`), `priority`, `clearance`, `minWidth`, `padConnection`, `thermalGap`, `spokeWidth` and `locked`; a text `x`, `y`, `rotation`, `locked`, `layer`, `text`, `height`, `width`, `thickness`, `bold`, `italic`, `knockout`, `hAlign`. A set of another kind's key, or one the item refuses, answers `bad_args` (`message` says why), and so does a set the engine refuses (a layer the board does not use, a bound KiCad keeps).
- The change is ONE edit, as KiCad's own properties panel makes one: one undo step, the board modified, and an `ev.edited` after the answer. The answer is `{ item }`, the item read back once the engine's apply queue is empty and the read shows the change (within KiCad's rounding: lengths to 4 decimals, angles to 3, a rotation by its angle). A copper area's change does not pour it again (KiCad's default).
- The checks, in order, every one before any effect: as for `board.explain` (the engine with `kicadBoardItemGet`, `kicadBoardItemSet` and `kicadCollabBusy`); for a set, then the item (`not_found`, `message` the uuid, when the board does not hold it) and its own refusals (`bad_args`). `not_applied` when the read back does not show the change within about 5 s. While a `board.check` runs, `board.item.set` answers `busy` and `board.item.get` is answered once the editor is free.
- Why engine exports (2026-11-10): the island reached a board item's properties only through KiCad's own dialogs, which it never shows. So the engine gained `kicadBoardItemGet(uuidsJson)` and `kicadBoardItemSet(argsJson)`, each set ONE `BOARD_COMMIT` through the item's own setters (pcbjam `cc/main` 70fe8e2; engine run 12).
- Measured over the local pair with engine run 12 built locally (2026-11-10, `tests/e2e/board-item.spec.ts`): `board.item.get` of one footprint answers in 0.3 to 1.1 ms (medians of 5, Chromium then Firefox, on drc-small and Glasgow); a set reads back in 11 to 22 ms on drc-small (medians per kind) and 40 to 42 ms on Glasgow's U1; every key of every kind read back as sent, each one undo step with one `ev.edited`, Ctrl+Z (`key.press`) taking the last one back.

### keys.claim
Claims Alt chords for the host (island `v0.2.3-cc17`, the `hostKeys` cap): while the reader's keyboard focus is inside the frame the host page sees no key, so the frame hands it the chords it claimed as `ev.key` (below). Each chord means Alt held with the key `code` names, Ctrl and Meta not held; `shift: true` means with Shift, `shift` absent or `false` without it. `code` is a `KeyboardEvent.code`: `KeyA` to `KeyZ`, `Digit0` to `Digit9`, `Slash`, `Period`, `Comma`, `Semicolon`, `Quote`, `BracketLeft`, `BracketRight`, `Backslash`, `Minus`, `Equal` or `Backquote` (the physical key, whatever the layout types). A claim replaces the whole claimed set: `{ chords: [] }` claims nothing, and a host that never claims (an older host) gets every key handled exactly as before. At most 64 chords; an unknown field, a code outside the list, a `shift` that is not a boolean, a `chords` that is not an array or one over 64 answers `bad_args` and the set claimed before stays.

The frame never takes KiCad's own Alt chords, its default hotkeys in either editor (`DefaultHotkey( MD_ALT + ... )` in KiCad 10's `common/tool/actions.cpp`, `eeschema/tools/sch_actions.cpp`, `pcbnew/tools/pcb_actions.cpp` and `pcbnew/router/router_tool.cpp`): Alt with `KeyS`, `KeyW`, `KeyZ`, `Digit1`, `Digit2`, `Digit3`, `Digit4` or `Backquote` without Shift, and Alt with Shift and `Comma` (KiCad's Alt+<) or `KeyV`. Such a chord is left out of the set and answered back in `refused`, each once, in the order asked, as `{ code, shift }` with `shift` always a boolean; `claimed` counts the distinct chords taken. It is answered at once, before the engine is up too, and the set holds until the next claim or the frame's end.


### shutdown
Releases the engine before the host removes the frame: the document is dropped (no `ev.saved` from here on, and the leave prompt stays quiet), every parked engine activation is unwound, the engine's threads are stopped, its WebGL contexts are released and its globals and window are cleared. The answer `{}` is the last message on the port: the frame then closes the port, answers nothing else (requests sent behind the shutdown included) and emits nothing, `ev.closing` included. The editor is not usable afterwards; the host removes the frame (or reloads it to start again). If the teardown fails the answer is `island_error`, and the port closes all the same. A shutdown sent before `ev.ready` stops the engine at its first park; the host still removes the frame. The host waits for the answer with a timeout (5 s, say) and removes the frame when it expires: in a background tab the browser may throttle the teardown's timers far past that, and the removal's `pagehide` covers the release.

Without the op, removing or navigating the frame runs a shorter teardown from `pagehide`: every parked engine activation is refused and unwinds before the document goes, and the rest (the threads, WebGL, the globals and the window) is left for the browser to release with the document.

## Events (frame to host): `{ type: string, ... }`
Each event carries exactly the keys listed here.

- `ev.state { phase: string, detail?: string }`; `phase` is one of `preflight`, `booting`, `staging`, `opening`, `blocked`, `fatal`, `popup`. `detail`, when present, is one of the island's own short strings, never engine or loader text:
  - `blocked`: the browser cannot run the engine; `detail` lists the failed capability codes, space separated (`no-sab`, `no-wasm`, `no-threads`, `no-webgl2`).
  - `fatal`: the engine stopped and the frame shows its fatal screen; `detail` is one of `memory` (out of memory), `crash` (the engine aborted; an import whose call trapped sends no `fatal`, its `import_failed` answer says so, `project.import` above), `boot_failed`, `engine_timeout` (no editor window within the boot time limit), `no_container`, `webgl_lost` (the browser lost the editor's WebGL context, for example on a GPU reset). The host reloads the frame to start again.
  - `popup` is informational: `ev.state { phase: "popup", detail: "<n> popup attempts blocked" }` may arrive at any time after `ev.ready`, once for every blocked popup attempt (`<n>` is the running count). It never changes the host's state. Attempts made before `ev.ready` are reported once, as a `booting` detail in the same words.
  - `booting`: while the engine's files load, `booting` repeats at most once every 2 s with `detail` the whole percent loaded, digits only (`0` to `100`), so a host that bounds the boot by inactivity sees it is still moving. Neither the first nor the 100 percent tick is promised.
  - `staging` and `opening` mark a `project.open` or a `project.import` in progress.
- `ev.ready { caps: string[], engine: { tag: string, kicad: string } }` once, after the engine booted and its editor window is up, and before any `project.open`: the host opens its project after this event. `caps` are the engine export names found on `Module`, sorted, and the pseudo-cap `picker` exactly when the fast part picker is live (`lib.index`, `lib.item`, `lib.prefetch`, `place` and `ev.pick`): the island's library mirror loaded and the engine has `kicadPlaceImportedItem` and `kicadCollabGetSelection`. On the example library (no mirror) `picker` is absent, the place keys stay KiCad's and no `ev.pick` is sent. A host gates its picker on `picker` (with `kicadPlaceImportedItem`), never on the export alone, which older islands list too. The pseudo-cap `selection` (island `v0.2.3-cc9`) is listed exactly when selection runs both ways: the engine has the selection hook for `ev.selected` (its `kicadCollabPresenceStart`) and `select` has its exports; a host gates both on it, never on the exports, which older islands list too. The pseudo-cap `write` (island `v0.2.3-cc10`) is listed by every island that answers `project.write` (it needs nothing of the engine but its file system); a host gates its writes on it. The pseudo-cap `fields` (island `v0.2.3-cc11`) is listed exactly when `picker` is, by islands whose `place` takes `value` and `footprint`; a host sends them only under it. The pseudo-cap `identity` (island `v0.2.3-cc11`) is listed exactly when `picker` is, by islands whose `place` takes `mpn` and `manufacturer`; a host sends them only under it (a local cc11 build of the morning of 2026-10-26 lists `fields` and refuses them). The pseudo-cap `projectLibs` (island `v0.2.3-cc12`) is listed when `project.libs` answers: the engine has `kicadLibsAddEntry`, `kicadLibsReload` and `kicadCollabBusy` (every engine since PCBJam v0.2.3 has them, so the word, never the exports, says the island takes the op). The pseudo-cap `models` (island `v0.2.3-cc12`) is listed when `footprint.models` answers: the engine has `kicadFootprintSetModels` (our engine build from pcbjam `cc/main` 466a85a on), `kicadCollabTestItemBlob` and `kicadCollabBusy`, in either frame's kind (a `sch` frame answers `unsupported`); a host gates the op on it. The pseudo-cap `plot` (island `v0.2.3-cc13`) is listed when `project.plot` answers: the engine has `kicadPlotBoard` (our engine build from pcbjam `cc/main` 924d67c on) and `kicadCollabBusy`, in either frame's kind (a `sch` frame answers `unsupported`); a host gates the op on it. The pseudo-caps `symbol`, `annotate` and `check` (island `v0.2.3-cc15`) are listed when `symbol.get` and `symbol.set`, `sheet.annotate` and `sheet.check` answer: the engine has `kicadSymbolGet` and `kicadSymbolSet`, `kicadAnnotate`, and `kicadCheckSheet` (our engine build from pcbjam `cc/main` e8b2abe on, engine run 10), each with `kicadCollabBusy`, in either frame's kind (a `pcb` frame answers `unsupported`); a host gates each on its word. The pseudo-cap `properties` (island `v0.2.3-cc16`) is listed by a `sch` frame exactly when its engine has `kicadHostProperties` (our engine build from pcbjam `cc/main` b1b5635 on, engine run 11): its schematic editor asks the frame before KiCad's symbol properties dialog opens, and the frame sends `ev.properties` instead (below); a `pcb` frame never lists it. A host that lists its own properties window gates it on this word. The pseudo-cap `hostKeys` (island `v0.2.3-cc17`) is listed by every frame that answers `keys.claim` and sends `ev.key`: they need nothing of the engine. A host gates its claim on this word. The pseudo-caps `boardUpdate`, `drc`, `explain` and `boardItem` (island `v0.2.3-cc19`) are listed when `board.preview` and `board.update`, `board.check`, `board.explain`, and `board.item.get` and `board.item.set` answer: the engine has `kicadUpdateBoardFromSchematic` and `kicadCollabBusy`, `kicadCheckBoard` and `kicadCollabBusy`, `kicadExplainViolation`, and `kicadBoardItemGet`, `kicadBoardItemSet` and `kicadCollabBusy` (our engine from run 12), in either frame's kind (a `sch` frame answers them `unsupported`). `boardProperties` is listed when the engine has `kicadHostBoardProperties` (a `pcb` frame then sends `ev.boardProperties`), and `heldKeys` when it has `kicadHostActions` (the frame then sends `ev.held`), each in either frame's kind. A host gates each on its word. `engine.tag` is the PCBJam release tag the engine was built from; `engine.kicad` is the KiCad version string (for example `10.0`), not a commit.
- `ev.saved { path: string, bytes: Uint8Array }` after every save of a file in the project folder, whether the user pressed Ctrl+S or the host sent `project.save` (or `project.import`, for its converted board). One Ctrl+S, and one `project.save` in a schematic, emits several (each sheet file of a schematic and its `.kicad_pro`; a board's Ctrl+S, the `.kicad_pro` beside the board). A file saved outside the project folder (a Save As elsewhere) is not reported. None is emitted after `project.forget` until the next successful `project.open`.
- `ev.openTool { frame: "sch" | "pcb" }` when the editor's own Switch or Quit menu asks for the other frame; the frame does not navigate.
- `ev.help { topic: string }` when the editor asked to open a KiCad help page; `topic` is the last path segment of the KiCad docs URL, `[a-z0-9_-]{1,64}`.
- `ev.menu { open: boolean }` when something of KiCad's own is drawn over its canvas: `open: true` when a popup menu (a context menu, KiCad's clarify-selection menu) or any dialog (a wx type whose name contains `Dialog`, progress dialogs included: an import's dialogs report it too) shows while none was up, `open: false` when the last of them closes. A host hides what it draws over the frame while it is open, so the menu or dialog is not covered. A popup menu is reported at once, a dialog within about 100 ms. Nothing is sent while nothing is up, nor after `shutdown` was answered or the frame went away.
- `ev.chrome { shown: boolean }` with KiCad's own chrome as the engine reports it: `shown: true` while its menu bar, its status bar or any pane but the canvas shows, `false` while none does. Sent once after `ev.ready` with the state the boot left (hidden), then each time it flips, which with the chrome hidden happens only through `chrome.show`: the engine holds the hidden chrome (a pane toggle such as Ctrl+H, a pane's close button, a save, a load or a theme change re-hides at once). A host renders its menus control from this event, never from its own toggle alone. Only from an engine with `kicadChromeShown` (our engine from run 9, pcbjam `cc/main` 27d82c2); an older one sends none. Nothing is sent after `shutdown` was answered or the frame went away.
- `ev.edited { depth: number }` when the open document's undo depth changes. The frame reads KiCad's undo command count every 500 ms while a document is open (from a successful `project.open` or `project.import` until `project.forget` or the next open), no dialog is up (progress dialogs included), no load is parked and no request is in flight (from its arrival to its answer, the whole of a `project.import` included), and sends it when it differs from the last value read. `depth` is a whole number of at least 0: an edit raises it, an undo lowers it, a redo raises it again. A host reads any `ev.edited` as "the document changed" and never as a promise that unsaved changes exist: KiCad's undo list stops growing at its limit, and a save leaves it as it is. Each read is compared with the last one only, so an undo followed by a new edit inside one read interval leaves the depth unchanged and is not sent, as is an edit made once the list has stopped growing: a host keeps a periodic save as well. The first value read after an open or an import is the baseline and is not sent (opening a document is no edit); when the open answers while its load is still parked on a KiCad dialog (the file-version confirm on an older file), the baseline is the first value read once that load has settled, never one read while it was parked; a change made while a request was in flight is sent after that request's answer. An engine without the `kicadCollabTestUndoDepth` export (absent from `ev.ready` `caps`) sends none, and nothing is sent after `shutdown` was answered or the frame went away. Added in island `v0.2.3-cc6`.
- `ev.pick { kind: "symbol" | "footprint", power?: true }` when the reader pressed KiCad's place key inside the frame: `A` in a `sch` frame (`kind: "symbol"`), `P` in a `sch` frame (`kind: "symbol", power: true`), `A` in a `pcb` frame (`kind: "footprint"`). The key counts by the character it types, in either case, with no Ctrl, Alt, Shift or Meta held, only while nothing of KiCad's own is over its canvas (no popup menu, no dialog but a progress dialog, no other window of KiCad's such as its footprint chooser), no text field has the keyboard focus and no `project.import` runs, and only when `ev.ready` listed `picker` (without the mirror the keys are KiCad's, as before). The frame takes the key from KiCad (its keydown, keypress and keyup), so KiCad's chooser never opens, and sends one `ev.pick` per press (a held key's repeats send none); the host opens its own picker and places with `place`. A `key.press` of those keys from the host does the same. `power` is present only when true. KiCad's own choosers stay reachable through its menus (`chrome.show`). Added in island `v0.2.3-cc7`.
- `ev.selected { uuids: string[], fpPaths: string[] }` when the editor's selection changed and has settled: `uuids` are the selected items' uuids in KiCad's order, `fpPaths` each selected footprint's schematic path (`/<sheet uuid>/.../<symbol uuid>`, a board only: always `[]` in a `sch` frame, and a footprint with no path has none); an emptied selection sends `{ uuids: [], fpPaths: [] }`. It comes from the engine's own selection hook (`window.kicadCollab.onSelection`, armed once through `kicadCollabPresenceStart`: at `ev.ready` in a `pcb` frame, at the first successful `project.open` or `project.import` in a `sch` frame, for the engine's collab document listener the call registers; `bridge/selection.ts` says why), which the engine fires after each press, key or wheel in the drawing and each change to the document has been handled, and from reads of the selection about 0, 200 and 600 ms after each pointer or key release in the frame (a selection made in KiCad's clarify-selection menu raises no hook). A burst is sent once, about 150 ms after it settled, and only when it differs from the last selection sent; a `select` the host sent arrives the same way. Sent only while a document is open (from a successful `project.open` or `project.import` until `project.forget` or the next open; nothing while an import runs), and every document starts with an empty selection, which is never sent: the first `ev.selected` after an open names a selection. Only when `ev.ready` listed `selection`. Added in island `v0.2.3-cc9`.
- `ev.properties { uuids: string[], sheetPath: string }` when the reader asked for a symbol's properties in a `sch` frame: a double-click on the symbol, its `E` key over it or its context menu's Properties, on the symbol's body, one of its pins or one of its fields (a lone pin or field counts as its symbol). `uuids` holds exactly the symbol's uuid; `sheetPath` is the sheet it sits on in `project.open`'s form (`/` for the root, then one uuid and a slash per level), the form `symbol.set` requires and `sheet.enter` takes. KiCad's symbol properties dialog does not open, and the symbol stays the one selected, so `ev.selected` names the same uuid (a pin or field selection gives way to its symbol). Sent only while a document is open (from a successful `project.open` or `project.import` until `project.forget` or the next open), after `ev.ready`, and never after `shutdown` was answered; outside that, and for every other item (a label, a wire, a sheet, text), KiCad's own dialog opens as before and `ev.menu` reports it. Only from an engine with `kicadHostProperties` (our engine from run 11: kicad `cc/main` ffe73d65, the hook in `SCH_EDIT_TOOL::Properties`, pinned by pcbjam `cc/main` b1b5635; island `v0.2.3-cc16`), where the frame lists the `properties` cap; an older one sends none and KiCad's dialog opens. `field` (island `v0.2.3-cc19`), 1 to 128 characters, is present only when KiCad named one of the symbol's fields: the U, V and F keys over a symbol (Edit Reference, Value, Footprint; our engine from run 12 asks first there too, `editFieldText`) send `Reference`, `Value` or `Footprint`, and a lone field selected sends its own name; the host opens its form on that field. A name past 128 characters is left out and the symbol taken all the same.
- `ev.boardProperties { uuid: string, kind: "footprint" | "track" | "arc" | "via" | "zone" | "text" | "marker" }` (island `v0.2.3-cc19`, the `boardProperties` cap) when the reader asked for one board item's properties in a `pcb` frame: a double-click on it, its `E` key or its context menu's Properties, on one footprint (a field or text of it counts as its footprint), track, arc, via, copper area (not a keep out area), board text or a check's mark. KiCad's dialog does not open (for a mark, KiCad's design rules checker) and the item stays the one selected, so an `ev.selected` naming it follows when the selection changed. Sent only while a document is open, after `ev.ready`, never after `shutdown` was answered; anything else (a pad, a drawn shape, a dimension, several items) opens KiCad's own dialog as before. Only from an engine with `kicadHostBoardProperties` (our engine from run 12: the hook in `EDIT_TOOL::Properties`).
- `ev.held { action: string }` (island `v0.2.3-cc19`, the `heldKeys` cap) when the reader pressed a KiCad hotkey whose window the host replaces: our engine (from run 12, `ACTION_MANAGER::RunHotKey`) asks the frame before a hotkey runs its action, and the frame takes these, in these frames, only while `ev.ready` listed the cap beside each: `common.Control.updatePcbFromSchematic` (F8; both frames; `boardUpdate`), `pcbnew.DRCTool.runDRC` (`pcb`; `drc`), `eeschema.InspectionTool.runERC` (`sch`; `check`), `eeschema.EditorControl.annotate` (`sch`; `annotate`), `common.Control.show3DViewer` (Alt+3; `pcb`), `eeschema.EditorTool.showHierarchy` (Ctrl+H; `sch`), `pcbnew.Control.showLayersManager` (`pcb`), `common.Control.showProperties` (both frames) and `common.Control.showDatasheet` (D; `sch`), the last five under `heldKeys`. The action does not run, so its window never opens; one `ev.held` per press (a held key's auto repeats are taken and send nothing). Every other key runs as before, and KiCad's own menus (behind `chrome.show`) still reach every action. Sent only while a document is open, after `ev.ready`, never after `shutdown` was answered. A `key.press` from the host of such a key is held and sent the same way, as a reader's press is. The merged engine asks for both editors' actions in either frame (in a board, `E` asks `eeschema.InteractiveEdit.properties` first): the frame answers by its own kind's table, so another editor's action is never taken. Measured over the local pair with engine run 12 (2026-11-10, `tests/e2e/held.spec.ts`, Chromium and Firefox): each of the nine sends its `ev.held` and opens no window (no `ev.menu`), `E` on a footprint, a track, a copper area and a board text sends `ev.boardProperties`, `E` on a pad still opens KiCad's pad dialog, U, V and F send `ev.properties` with `Reference`, `Value` and `Footprint`, and Ctrl+F still opens KiCad's Find.
- `ev.key { code: string, shift: boolean }` (island `v0.2.3-cc17`, the `hostKeys` cap) when the reader pressed a chord the host claimed through `keys.claim` with the frame's keyboard focus: once per press (a `keydown` that is no auto-repeat) with Alt held, Ctrl and Meta not, whose `code` and Shift state match a claimed chord. The frame cancels that `keydown` and stops it in the capture phase on its window, before any of the engine's listeners reads it, and does the same to its `keypress`, its `keyup` (released in any order with Alt) and its auto-repeats, so KiCad never sees any part of the chord and the browser never acts on it (Alt+F opens Chrome's menu otherwise). A plain key, a chord with Ctrl or Meta, an Alt chord not claimed and every key the frame dispatches itself for `key.press` (a claimed chord included) go to KiCad as before; nothing else is ever forwarded.
- `ev.closing {}` on `pagehide`, and when the user chooses File > Quit (the frame then shows its fatal screen and navigates nowhere). Sent at most once, and never after `shutdown` was answered.

Unknown fields are rejected by both sides. An unknown event `type` is ignored by the host; an unknown `op` is answered `unknown_op`.

## Leaving the frame
KiCad asks "Leave site?" when the frame unloads with unsaved edits. The frame keeps that prompt quiet when the host is about to reload it and nothing would be lost:
- for 10 s after a `project.save` that emitted `ev.saved`, or a successful `project.import` (the host has the bytes);
- from `project.forget` until the next successful `project.open`, whatever the forget answered (`island_error` included).

A Ctrl+S in the editor does not quiet it, and outside these windows a reload with unsaved edits still gets the prompt.

## island.json
Each island release serves `island.json` beside its page, and the island host serves the current one at `/island.json`:

| field | meaning |
|---|---|
| `id` | the islandId, `^[a-z0-9][a-z0-9.-]{0,63}$`; the release's path is `/r/<id>/` and its source is the release tagged `<id>` |
| `tag` | the PCBJam release tag the engine was built from (the same value as `ev.ready` `engine.tag`) |
| `kicadCommit` | the KiCad source commit the engine was built from (a full SHA), not a version string |
| `source` | the address of this release's source |
| `ops` | the request ops this release answers, sorted (island `v0.2.3-cc13`; absent from older releases): a host learns from it that a release answers `project.plot` before any engine boots, and treats an absent `ops` as answering none of the ops added since |

A host needs only `id`.

## Versioning
`proto` is the major. A host that sees a major it does not know ignores the hello. New ops, events, error codes and `island.json` fields are added within a major; removing or changing one bumps it. `ev.edited` (island `v0.2.3-cc6`) is such an addition: a host that does not know it ignores it, and a host facing an older island never receives it. So are `ev.pick`, `lib.index`, `lib.item`, `lib.prefetch`, `place` and `not_found`, with one change an older host does meet: the island takes KiCad's place keys (`A`, and `P` in a schematic) for `ev.pick`, which an older host ignores, so the reader's `A` does nothing there. The host that handles `ev.pick` ships before the island that sends it; it finds an older island by the absent `picker` cap and keeps pressing KiCad's keys for it. `ev.selected` and `select` (island `v0.2.3-cc9`) are additions too: a host finds an older island by the absent `selection` cap. `project.write`, the error code `open_document` and the `write` cap arrive with island `v0.2.3-cc10`: a host finds an older island by the absent `write` cap. `place`'s `value` and `footprint` and the `fields` cap arrive with island `v0.2.3-cc11`: a host finds an older island by the absent `fields` cap. So do `place`'s `mpn` and `manufacturer` and the `identity` cap: a host finds an island without them by the absent `identity` cap. `project.libs` and the `projectLibs` cap, and `footprint.models` and the `models` cap, arrive with island `v0.2.3-cc12`: a host finds an older island by the absent cap, and an island whose engine lacks `kicadFootprintSetModels` by the absent `models` cap. `project.plot`, the error code `plot_failed`, the `plot` cap and `island.json` `ops` arrive with island `v0.2.3-cc13`: a host finds an older island by the absent `plot` cap, or before any engine boots by an `island.json` whose `ops` is absent or does not list `project.plot`. `symbol.get`, `symbol.set`, `sheet.annotate`, `sheet.check`, the `symbol`, `annotate` and `check` caps, and `not_found` for a The islandId is also the cache key: `/r/<id>/` is served `immutable`, and the loader checks no engine byte. So an engine is never rebuilt under an islandId that has been released or shipped: a new engine build after a release or a ship takes a new islandId. A local engine swap under the same id (`fetch-engine --local` and `npm run build`, as runs 4 and 5 both served `v0.2.3-cc8` before any release) is tested only after the editor origin's cache is cleared (its site data, or a fresh browser profile), and the frame's console line `[build] wasm kicad_editor/v0.2.3/kicad_editor.wasm etag=<...> head128k-sha256=<first 24 hex of the sha256 of the wasm's first 128 KiB> streamed=<bytes on the wire>B` proves which bytes ran: engine run 5 prints `head128k-sha256=75d7ed733cca05d0855cb1ee streamed=16662766B` (the gzip body both the local pair's nginx and `tests/serve.mjs` send; run 4 printed `177b858177f01840ef73d12b` and `16662560B`).
